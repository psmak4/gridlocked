## Part 0. Conventions (proposed)

### 0.1 Naming
- **Tables are plural snake_case** (`events`, `sessions`), and columns are snake_case. Foreign keys are named `<thing>_id`.
- **Better Auth's tables are renamed** through its model-name settings, so they don't collide with ours or with Postgres reserved words:
  - `user` → `users`, because `user` is reserved in Postgres;
  - `session` → `auth_sessions`, because `sessions` means race sessions here;
  - `account` → `auth_accounts`;
  - `verification` → `auth_verifications`.

  Phase 4 will confirm this renaming works with the admin plugin.

### 0.2 Keys
- **Primary keys are UUIDv7, generated by the app** (proposed).
  - **Why:**
    - They're safe to show in URLs; a sequential ID would leak counts of users and posts.
    - Seeding and the 2026 replay harness can create rows offline without colliding.
    - UUIDv7 is time-ordered, so indexes stay compact, unlike random UUIDv4.
    - We don't depend on Postgres 18's built-in `uuidv7()`.
  - **Alternative:** `bigint` identity keys. They're smaller and faster to join, but they'd need a separate public ID for URLs.
  - **Better Auth** is set to generate UUIDs too, so `users.id` matches everything else.
- **Natural keys get unique constraints** even though they're not the primary key. Examples: `(season_id, round)` on events and `(event_id, kind)` on sessions.
- **Slugs** (`max-verstappen`, `2027-monaco`) are unique and used in URLs. They're never used as foreign keys, so they can be changed.

### 0.3 Types
| Kind of value | Type | Notes |
|---|---|---|
| Timestamps | `timestamptz`, stored in UTC | Displayed in the user's timezone. Event pages can also show circuit local time |
| Calendar dates (e.g. date of birth) | `date` | |
| Status and kind fields | `text` plus a `CHECK` constraint listing allowed values | Easier to change than Postgres enums. Drizzle's `text({ enum })` gives the TypeScript type |
| Money (prices, budget, bank) | `integer`, in **units of $0.1M** | $23.4M is stored as `234`; the $100M cap is `1000`. Exact arithmetic and no floats. Every official price is a multiple of $0.1M (verify in Part 3) |
| Fantasy points | `integer` | Official scoring has no fractional points; multipliers are stored as integer deltas |
| Flexible parameters | `jsonb`, validated by a Zod schema in the app | Only for versioned config such as rule parameters. Never for data we query by |

### 0.4 Row history and deletes
- **Mutable tables have `created_at` and `updated_at`.**
- **Nothing is soft-deleted with an `is_deleted` flag.** Things that can be withdrawn get a real status instead, such as a post being `removed` or an event being `cancelled`, so queries say what they mean.
- **Hard deletes are only for privacy requests** (GDPR/CCPA, HLD §13.6) and for data with a retention policy, such as chat (Part 5).
- **Versioned things are append-only:** lineup versions, ruleset versions, price history and raw snapshots. A version row is never updated after the moment it takes effect.
- **Admin changes are written to `audit_log`** (Part 6) in the same transaction as the change.

### 0.5 Layers never mix (decided, HLD §3.3)
- Reference (Part 1), results (Part 2) and game data (Parts 3–4) live in separate tables.
- Foreign keys only point **down** the stack: game → results → reference. Results never hold points, and game tables never edit results.
- **Spoiler scoping:** every row that reveals a session's outcome carries a `session_id` or `event_id`, so spoiler filtering is a join, not guesswork (HLD §7.3).

### 0.6 How each part is checked
Every part ends with the same three checks before it comes to you for review:

1. **A scenario table.** Each real situation the part must survive is listed, with how the model handles it. Real cases come from F1 history, plus anything we can verify in the 2026 data. A scenario that *isn't* handled is listed as a known limit with what fixing it later would cost; it isn't left out. Part 1's table is in 1.14.
2. **A scale table.** Row counts at three sizes, plus the hot queries and the indexes that serve them:
   - beta: about 500 users and 1,000 teams;
   - established: about 10k users and 25k teams;
   - big: about 100k users and 250k teams.

   The free tier only has to carry the beta. The larger sizes have to work without a redesign, though they may need paid plans.
3. **A change test.** For the changes we can foresee, the part says what kind of change each would be:
   - **config only:** a row in a versioned config table;
   - **additive migration:** a new column or table, with nothing rewritten;
   - **redesign:** existing data has to be reshaped.

   Redesigns are what the model is built to avoid. Each one that remains is called out with a reason.

### 0.7 Sturdiness rules (apply everywhere)
- **The database enforces the rules that matter, not just the app.** That means foreign keys, `CHECK` constraints, unique and exclusion constraints, and the lock trigger in Part 3. A bug in one API route then can't corrupt the data.
- **Foreign keys default to `ON DELETE RESTRICT`.** Cascades are used only for true children, such as a lineup version's picks. Accidentally deleting a parent fails loudly instead of silently taking history with it.
- **Admin edits use optimistic concurrency.** Editable rows carry a `version` integer, and a save that started from a stale version is rejected. Two admins resolving the same queue item can't overwrite each other.
- **Writes from jobs are idempotent.** They use natural unique keys and `INSERT … ON CONFLICT`, plus a scoring run ID for replace-style writes (HLD §3.3).
- **Migrations are expand-then-contract.** Add the new column or table, backfill, switch reads, and only drop the old one in a later release. No migration needs downtime or a big rewrite under load.
- **Big tables are planned for partitioning from day one.** The team ledger, chat and raw snapshots get keys that let them be partitioned by season or month later without changing queries. Partitioning itself waits until a table is big enough to need it.
- **Derived data can always be rebuilt from source.** Standings, totals and caches are materialized for speed, but each one has a rebuild path from the ledger and results. A bad cache is a re-run, not a data repair.

### 0.8 Deliberately not flexible (so the model stays simple)
Being flexible everywhere makes everything harder. These limits are chosen on purpose, with the cost of changing them later:

| Limit | Why | Cost to change later |
|---|---|---|
| One series (F1). There's no `series` column | Jolpica is F1-only, and the product is F1-only | Additive: add a `series` table, a column on `seasons` and a changed unique key. Everything else hangs off seasons |
| One scoring ruleset per game, shared by every league. **No per-league scoring (decided 2026-10-27, yours)** | Lets asset scores be computed once and shared by all teams (HLD §5.6), which is what keeps scoring cheap at scale | **Redesign** of the ledger; accepted |
| ~~One game~~ **Kept open (decided 2026-10-27, yours).** Teams, leagues and the ledger belong to a `games` row (season + game type + ruleset + budget), not directly to a season. Launch has one game type, `season_fantasy` | A second game, such as a weekly prediction game, becomes new tables for its own mechanics, not a reshape of existing ones | Designed in Part 3 |
| No multi-tenancy (one site) | | Not planned |

### 0.9 Storage budget (free tier)
Neon's free plan allows 1 GB per project (HLD §11.4). The rough sizes below will be checked against measured row sizes in Part 4.
- Reference and results data is tiny: a season is a few thousand rows.
- The big tables will be the team ledger (Part 4), posts and chat (Part 5), and raw snapshots (Part 2).
- Each of those parts states its expected size and its retention rule.

### 1.3 `events` (a race weekend)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| season_id | uuid FK → seasons | |
| round | integer | Unique with `season_id`, and the constraint is **deferrable** so a whole calendar can be renumbered in one transaction. It's display order only: nothing else references an event by round (see below) |
| slug | text, unique | Built from the season and the event **name**, not the circuit: `2026-bahrain-grand-prix-in-malaysia`. A season can visit one circuit twice (2020 had two races each at the Red Bull Ring, Silverstone and Bahrain) |
| name | text | "Monaco Grand Prix". Facts used descriptively (HLD §13.4) |
| circuit_id | uuid FK → circuits | |
| format | text: `standard`, `sprint` | Sets which sessions are created by default. New formats are a new allowed value plus a session template in config |
| status | text: `scheduled`, `cancelled`, `completed` | `completed` is set by the finalizer (HLD §4.4) |
| lock_session_id | uuid FK → sessions, nullable | The session whose start locks the game: Qualifying, or Sprint Qualifying on sprint weekends. It's stored explicitly rather than inferred from `format`, so a new format can't silently move the lock |
| lock_at | timestamptz, not null | **The fantasy lock** (HLD §5.2). Defaults to `lock_session_id`'s scheduled start and follows it when that session moves, until an admin overrides it (audited) |
| lock_at_source | text: `default`, `admin` | Tells the sync job not to overwrite an admin's change |

Why `lock_at` is here and not in the game tables: it's a time the whole site uses, including thread modes, reminders and the scheduler's due-times file (HLD §4.5). Enforcement still happens in the game layer (Part 3).

**Cancelled, moved and renumbered events (verified with 2026 data).** Jolpica's 2026 calendar now has 23 rounds. The April races in Bahrain and Saudi Arabia are **gone from the feed entirely**. Every later round was **renumbered**: Miami is now round 4. A "Bahrain Grand Prix in Malaysia" runs at **Sepang** in October. So:
- **An event's identity is its row ID.** It isn't the round, the name or the circuit, since all three can change.
- **A cancelled event keeps its row**, with `status = cancelled`. It's never deleted, so threads, notifications and history that point at it stay valid.
- **The sync job never deletes.** An event that disappears from the provider goes to the admin queue as "missing from provider", and an admin marks it cancelled. A new or relocated event is matched by date and name first; when the match is uncertain, an admin confirms it.
- **Round renumbering changes only `round`.** Nothing else stores round numbers (see seats, 1.8).

What a cancellation does in the game (whether transfers are counted and whether chips are refunded) is settled in Part 3.

|---|---|---|

| season_id | uuid FK | |

**Rebrands:** a rename keeps the same constructor row with a new `display_name`. A genuinely new entrant gets a new constructor row. ### 1.8 `seat_assignments` (the expected line-up over a date range)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| season_id | uuid FK | |
| driver_id | uuid FK | |
| constructor_id | uuid FK | |
| car_number | integer | The number for that season |
| role | text: `race`, `reserve` | |
| valid_from | date | First day this seat applies |
| valid_to | date, nullable | Null means until further notice |

This is the "who drives for whom" list for the season. A mid-season swap **closes one range and opens another**; it never edits history.

**Ranges are dates, not rounds** (changed after checking the 2026 data). Round numbers move when the calendar changes, and in 2026 they did, after the seats were set. A date range keeps meaning the same thing when events are cancelled, added or renumbered. The admin UI still lets you pick "from the Dutch GP onwards" and stores that event's start date.

For the 2026 swap (HLD §8.1), effective from the Dutch GP (round 12, 2026-08-21):
- Lawson's `rb` seat closes, and a `red_bull` seat opens.
- Tsunoda's seat moves to `rb`.
- Hadjar's `race` seat closes.

**The swap was reversed from round 15** (Azerbaijan, first session 2026-09-24; verified in the recorded 2026 results, M2 Task 6). Hadjar returns to `red_bull` (#6), Lawson to `rb` (#30), and Tsunoda has no race seat. So the swap's seats run 2026-08-21 to 2026-09-23. The seat fixture `tests/fixtures/seats-2026.json` follows the data, and a test checks it against every recorded race.

**Constraint:** a driver can't hold two `race` seats in overlapping ranges. This is enforced with an exclusion constraint on `(driver_id, daterange(valid_from, valid_to))` for race seats. That needs the `btree_gist` extension, which Neon supports. A second exclusion constraint stops two race seats from using the same `car_number` at the same time.

### 1.9 `event_entries` (who is expected at this event)
| Column | Type | Notes |
|---|---|---|
| event_id | uuid FK | Composite PK with `driver_id` |
| driver_id | uuid FK | |
| constructor_id | uuid FK | |
| car_number | integer | |
| source | text: `seat`, `admin`, `results` | `seat`: copied from seat assignments when the event is created. `admin`: changed by an admin. `results`: seen in a session's results |

**Refinement of HLD §5.6 (proposed): event entries are the expected line-up, while scoring uses each result row's constructor.** The HLD says a constructor scores "whoever drove its cars at that event (from `entry` rows)". But substitutions can happen **mid-weekend**: a driver can fall ill after the sprint, or a reserve can start from FP3. Each result row from Jolpica already says which constructor the driver drove for **in that session** (verified in the samples). So:
- **Scoring:** a constructor's points come from the result rows that name it, session by session (Part 2).
- **Event entries** drive the team builder's warnings, the roster checker and the validator. A result row whose driver–constructor pair isn't in `event_entries` is a roster surprise, and it holds scoring for admin review (HLD §8.2).
- FP1 young-driver runs don't affect either, because practice isn't scored. The roster checker treats FP1 as a weak signal (HLD §8.2).
- **A mid-weekend substitution** (e.g. Bearman replacing Sainz from FP3 at Jeddah 2024): both drivers have entries for that event with the same constructor. The validator checks car counts **per session** against the results, not per event, so three drivers sharing two cars over a weekend is valid.
  - **Completeness (decided 2026-10-31):** a team is expected to run `min(its entries, validator_thresholds.carsPerConstructor)` cars. A session is complete when it has a row for every expected car. Only a team short of a car has missing drivers, and those are its absent entrants. The roster check uses the same rule on the latest practice session.

### 1.10 `driver_availability` (per-event status of pool drivers; decided, HLD §8.1)
| Column | Type | Notes |
|---|---|---|
| event_id | uuid FK | Composite PK with `driver_id` |
| driver_id | uuid FK | |
| status | text: `available`, `doubtful`, `unavailable`, `reserve` | |
| reason | text, nullable | Shown in the team builder, e.g. "Injured (wrist)" |
| source | text: `default`, `roster_check`, `admin` | |
| updated_at | timestamptz | |

Every pool driver gets a row for every event, created with `available`.

**This status is for people, not for scoring.** It drives the team-builder warning and the notifications. Scoring doesn't read it: a pool driver missing from a scored session's results gets the NC or no-time penalty because they're missing (HLD §6), whatever this table says. That keeps a stale status from ever changing points. "Who is in the pool" is a game fact, so the pool itself is in Part 3. This table holds only the real-world status.

### 1.11 `provider_ids` (only adapters read it; decided, HLD §3.3)
| Column | Type | Notes |
|---|---|---|
| provider | text: `jolpica`, `openf1`, … | |
| entity_type | text: `circuit`, `event`, `session`, `driver`, `constructor` | |
| provider_key | text | `max_verstappen`, `red_bull`, an OpenF1 `session_key`, or for Jolpica events `season/round` |
| entity_id | uuid | Our ID |

- **Constraints:** unique `(provider, entity_type, provider_key)`, and unique `(provider, entity_type, entity_id)`.
- **This is a deliberate exception to "every relationship is a foreign key":** `entity_id` points at a different table depending on `entity_type`. The adapter code checks it, and a nightly integrity job reports orphans.
- **Jolpica event keys aren't stable**, because rounds get renumbered (1.3). The adapter re-matches events on every sync by season, date and name, and updates the key. A key that would move to a different event of ours goes to the admin queue instead of being applied.
- **Switching to another provider** (e.g. Sportradar) means adding rows here, not changing other tables.

| Team renamed | Sauber → Audi; AlphaTauri → RB | New `display_name` per season, or a new constructor if it's a new entrant (1.7) |

| Mid-weekend substitute | Bearman for Sainz, Jeddah 2024 | Both have entries; cars are counted per session; scoring uses result rows (1.9) |
| Injured pool driver | Any | Availability is for warnings only; missing from results means the penalty applies (1.10) |
| Driver known by another name | Kimi Antonelli; family-name-first names | `display_name` (1.5) |
| Car number reused or changed | A champion running #1, then going back to their own number | The number lives on the seat, and two race seats can't share it at once (1.8) |
| Historical seasons for hub pages | 1950 onwards from Jolpica | The same tables work for any year. About 1,100 races × about 25 rows is tiny |
| A third car per team | Proposed in the past, never adopted | Nothing assumes two cars; the validator's car count is config |

**Known limit:** a constructor renamed **during** a season, which hasn't happened in modern F1, would show one name for the whole season. Fixing it would be additive: give `constructor_seasons` date ranges like seats have.

### 1.15 Scale
Reference data is tiny at every size: a season is about 24 events, 150 sessions, 30 drivers, 11 teams and about 600 availability rows. History back to 1950 adds tens of thousands of rows. User numbers don't change any of it, so its indexes are about query shape, not volume (1.13).

## Part 2. Ingestion and results (proposed)

This part covers how provider data comes in, becomes trusted per-session facts, and gets corrected. It holds **facts only, never points** (0.5). It also defines the job table that every background task uses, and the admin review queue that the validator and roster checker feed.

```mermaid
erDiagram
  provider_requests }o--o| raw_snapshots : "produced"
  raw_snapshots }o--o| sessions : "about"
  sessions ||--|| session_result_state : has
  sessions ||--o{ results : has
  raw_snapshots ||--o{ results : "normalized from"
  sessions ||--o{ result_overrides : has
  sessions ||--o{ result_changes : logs
  sessions ||--o{ session_participants : has
  review_items }o--o| sessions : "about"
  jobs }o--o| jobs : "spawned by"
```

**How it flows:**
1. A job calls a provider through the shared HTTP client, and the call is logged (`provider_requests`).
2. A response with new content becomes an immutable `raw_snapshot`.
3. The normalizer turns the newest snapshot for a session into `results` rows, and logs what changed since the previous snapshot (`result_changes`).
4. `effective_results` is a view: provider rows with admin overrides applied. **Scoring, results pages and results posts all read the view.** Nothing reads `results` directly.
5. The validator checks the effective results. A problem opens a `review_item` and holds the session's status at `under_review`.

### 2.2 `raw_snapshots` (exactly what a provider said; append-only)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| provider | text | |
| endpoint | text | |
| params_hash | text | Hash of `(provider, endpoint, params)`: "the same question" |
| content_hash | text | SHA-256 of the response body after canonical JSON formatting, so key order doesn't count as a change |
| body | jsonb | The provider's response, unchanged. Stored with lz4 TOAST compression (confirm Neon supports it in phase 4) |
| body_bytes | integer | For the storage dashboard |
| first_fetched_at | timestamptz | |
| last_seen_at | timestamptz | Updated when the same content is fetched again |
| season_id, event_id, session_id | uuid FKs, nullable | What the snapshot is about, when the adapter knows. Calendar and driver-list snapshots have only `season_id` |

- **Unique `(params_hash, content_hash)`.** The same answer to the same question is stored once. A refetch with unchanged content only bumps `last_seen_at` and logs an `unchanged` request.
- **Change detection comes free:** a new `content_hash` for the same `params_hash` means the provider changed something, such as a stewards' penalty (HLD §4.2).
- **The replay harness** (HLD §12) reads snapshots in `first_fetched_at` order under a simulated clock.
- **Retention:** kept permanently for the current and previous season, since they're the audit trail for points. Snapshots from bulk history imports (hub pages, 1950 onwards) can be dropped once normalized, because nothing scores them.
- **If it grows:** bodies can move to Neon Object Storage (5 GB free), leaving a `body_key` column. That's an additive change (2.11).

| classification | text: `classified`, `not_classified`, `disqualified`, `did_not_start`, `did_not_qualify`, `excluded` | Our canonical outcome (mapping below) |
| provider_status | text | Kept as given: `Finished`, `Lapped`, `Retired`, `Did not start`, … |
| provider_position_text | text | `1`, `R`, `W`, `D`, … |
| grid | integer, nullable | Sprint and race only. Null for a pit-lane start, with the flag below |

**Why one table rather than one per session type:** the scoring engine wants one shape ("give me this session's effective results"), and the fields barely differ. `CHECK` constraints keep session-specific fields where they belong, for example no `grid` on qualifying rows. Those checks need the session kind, so a trigger copies `sessions.kind` into the row on insert.

**Classification mapping (proposed; checked against 2026 data):**

| Provider says | `classification` | Note |
|---|---|---|
| numeric `positionText` (any status, including `Retired`) | `classified` | 7 drivers in the 2026 samples were `Retired` but still classified, because they'd completed enough distance |
| `R` or `N` | `not_classified` | |
| `D` | `disqualified` | |
| `E` | `excluded` | Rare. The ruleset decides whether it scores like a DSQ |
| `W` (status `Did not start`) | `did_not_start` | 7 such rows in the 2026 samples |
| `F` | `did_not_qualify` | Historical (107% rule) |
| Qualifying: driver listed with no times | `classified` with all Q times null | "No time set" is **derived** from `q1_ms is null`, not stored |

An unknown `positionText` value fails normalization and opens a review item. We don't guess.

**On a new snapshot,** the normalizer replaces the session's `results` rows in one transaction: it deletes them, inserts the new set, and updates `current_snapshot_id`. Earlier versions survive as snapshots and as `result_changes` rows.

### 2.6 `result_overrides` (the admin layer; decided, HLD §4.3)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| session_id | uuid FK | |
| driver_id | uuid FK | |
| kind | text: `patch`, `insert`, `suppress` | `patch`: replace some fields of the provider row. `insert`: a row the provider doesn't have, used for manual entry. `suppress`: ignore a bogus provider row |
| fields | jsonb | For `patch` and `insert`: only the fields being set, using `results`' column names. Validated by a Zod schema |
| reason | text, not null | Shown in the audit log, and in the score explanation when it affects points |
| created_by | uuid FK → users | |
| created_at | timestamptz | |
| revoked_at, revoked_by | nullable | Revoking reverts cleanly to the provider value |
| version | integer | |

- **At most one active override per `(session_id, driver_id)`**, enforced by a partial unique index `WHERE revoked_at IS NULL`. Editing one revokes it and creates the replacement, so history stays readable.
- **Why `jsonb` here, against rule 0.3:** an override sets an arbitrary subset of fields, and we never query by those fields. The Zod schema is generated from the `results` columns, so the two can't drift apart.
- **Manual entry of a whole session** (provider down, HLD §4.4) is a set of `insert` overrides, with `session_result_state.source = manual`. **If provider data arrives later,** the normalizer stores it as normal but **doesn't** remove the manual rows. It opens a review item instead ("provider data arrived; compare and choose"), and the admin either revokes the inserts or keeps them. Nothing changes silently.
- **One driver the provider left out** (Jolpica lists nobody with no Q1 time, so 2 of the 19 rounds of 2026 came back short) is one `insert` override, entered with `insertResult` (`pnpm staff insert`) beside `overrideResult` (`pnpm staff override`). It takes the session, driver, constructor, car number, position and classification, and a reason, and writes the audit row in its transaction. `provider_status` is `Entered by staff`, and `provider_position_text` is the position, or `-` with none. Running it again with the same values changes nothing; different values replace the active insert. It then checks the event again like every staff action, so the last missing driver takes the session from `awaiting` to `provisional`. It refuses a driver who has a provider row (that's a `patch`), one not in `event_entries` and a `final` session. `session_result_state.source` stays `provider`.

### 2.7 `effective_results` (a view; what everything reads)
- Provider rows with any active `patch` applied field by field, plus active `insert` rows, minus rows with an active `suppress`.
- Each row says whether it was overridden, so the UI and score explanations can show "corrected by admin: reason".
- **A plain view, not materialized.** A session is about 22 rows, so the join is trivial. Scoring snapshots what it read into its own run (Part 4), so a later override can't change a past run's explanation without a re-score.

| kind | text | e.g. `validation_failed`, `unknown_driver`, `team_change`, `missing_driver`, `event_missing_from_provider`, `uncertain_event_match`, `provider_after_manual`, `unknown_classification`, `provider_mismatch`, `score_mismatch`, `scoring_retried` |
| severity | text: `blocking`, `warning` | `blocking` holds scoring for the linked session; `warning` doesn't |

**Rule:** a session's status can't become `provisional` or `final` while it has an open `blocking` item. The status change is made in the same transaction as the check.

### 2.10 `jobs` (one table for all background work)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| kind | text | e.g. `poll_session`, `normalize`, `validate`, `score_session`, `finalize_check`, `roster_check`, `open_threads`, `send_notifications`, `price_update`, `sync_calendar` |
| dedupe_key | text | Unique with `kind`. Built so the *same* work can't be queued twice, e.g. `poll:<session_id>:<attempt>` or `open_threads:<event_id>` |
| payload | jsonb | Small; per-kind Zod schema |
| run_at | timestamptz | When it becomes due |
| status | text: `pending`, `running`, `succeeded`, `failed`, `dead` | `failed` is retried with backoff. After `max_attempts` it becomes `dead` and alerts admins |
| attempts, max_attempts | integer | |
| locked_until | timestamptz, nullable | A lease. If a worker dies mid-job, the lease runs out and another worker picks it up |
| last_error | text, nullable | |
| parent_job_id | uuid FK → jobs, nullable | For fan-out (below) |
| created_at, started_at, finished_at | timestamptz | |

- **How a job is claimed:** `UPDATE … WHERE id = (SELECT … WHERE status='pending' AND run_at <= $now ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT 1)`, with `$now` from the entry point's clock (HLD decision 20). Two workers, or two overlapping ticks, can never take the same job.
- **Calendar-driven work is planned ahead.** When an event is created or its times change, its jobs are written as `pending` rows with future `run_at`: open threads, flip chat modes, lock reminders, start polling, finalizer checks. A time change **updates `run_at`** of the matching pending job through its `dedupe_key`; nothing is deleted and recreated. The scheduler's due-times file is just "the next few `run_at` values" (HLD §4.5).
- **Fan-out is batched.** "Notify everyone in league X" or "score is final for 250k teams" is a parent job that spawns child jobs, each handling about 1,000 users or teams. No single job grows with the user count, and a failed batch retries alone.
- **Retention:** `succeeded` jobs are pruned after 30 days. `dead` jobs are kept until an admin clears them.

### 2.11 Configuration used by this part
These sit in a small `settings` table (key, Zod-validated value, `updated_by`, `updated_at`) and are audited:
- **Session durations** for defaulting `scheduled_end` (1.4). Proposed: practice 60 min, sprint qualifying 45 min, qualifying 60 min, sprint 45 min, race 120 min. An overrun is handled by `suspended` and by polling, not by the default.
- **The poll schedule:** start at scheduled end, then backoff 5 → 15 → 60 min, and give up after 24 h (HLD §4.4).
- **Finalizer checks:** +2 h, +6 h, +24 h and +48 h after the race (HLD §4.4).
- **Provider rate limits,** set below each provider's published limits (HLD §4.1).
- **Validator thresholds,** such as expected cars per constructor.

### 2.12 Indexes beyond keys
- `jobs (run_at) WHERE status = 'pending'`: the claim query and the due-times file.
- `jobs (status, finished_at)`: pruning and the admin "stuck or dead jobs" view.
- `raw_snapshots (params_hash, first_fetched_at DESC)`: "latest snapshot for this question".
- `raw_snapshots (session_id)`.
- `result_overrides (session_id) WHERE revoked_at IS NULL`: the effective view.
- `review_items (status, severity, created_at) WHERE status = 'open'`: the admin queue.
- `review_items (session_id) WHERE status = 'open' AND severity = 'blocking'`: the status-change guard.
- `provider_requests (requested_at)`: pruning and monitoring.

### 2.13 Scenario check
| Scenario | Real example | How it's handled |
|---|---|---|
| Time penalty after the race changes the order | Common; e.g. Alonso, Saudi Arabia 2023: penalised after the race, then reinstated the same night | A finalizer re-fetch gives a new content hash, so new rows and a `result_changes` log, then a re-score. The reversal is just another snapshot |
| Disqualification hours after the race | Hamilton and Leclerc both DSQ, China 2025; Russell, Belgium 2024 | Same path. `classification = disqualified`, and other drivers' positions move up |
| Change after the session is final | Appeals and right-of-review cases, days or weeks later | Admin reopens the session (audited) and triggers a re-fetch, or adds an override. Then a re-score |
| Provider data is wrong | A typo or a missing driver | The validator opens a `blocking` review item, and the admin fixes it with a `patch`/`insert`/`suppress` override with a reason |
| Provider down or late | Any | Poller backoff, give up after 24 h, then an admin alert and manual entry as `insert` overrides (2.6) |
| Provider data arrives after manual entry | Follows from the case above | Stored, but a review item asks the admin to choose. No silent swap (2.6) |
| Results published in stages | Partial classification while uploads finish | The validator treats "fewer drivers than entries" as **not yet complete** and keeps polling. It escalates to review only when the poll window ends |
| Q3 driver with no Q3 time | Round 18 2026: 9 Q3 times, 10 Q3 drivers (verified) | `position` is authoritative and `q3_ms` is null. Stage reached comes from position plus the ruleset's cut-offs (Part 3) |
| No time set in Q1, still allowed to start | Common after a crash in Q1 | Classified with null times; "no time set" is derived (2.4). Jolpica leaves such a driver out, so the session stays `awaiting` until staff enter them (`insertResult`, 2.6) |
| Excluded from qualifying, starts from the back | Hamilton, Brazil 2021 | Qualifying row is `disqualified`/`excluded`. The race row's `grid` is the real starting slot |
| Grid penalty | Common | `grid` is the actual starting grid, which is what positions gained/lost uses (HLD §5.6) |
| Pit-lane start | None in 2026 yet (verified) | `pit_lane_start = true`, `grid` null; synthetic test case |
| Retired but classified | 7 cases in the 2026 samples (verified) | Numeric `positionText` means `classified`, whatever the status says |
| Did not start | 7 `W` rows in the 2026 samples (verified) | `did_not_start`; the ruleset decides the penalty |
| Race abandoned, results from an early lap | Belgium 2021 | Session `abandoned` (1.4). Results stored normally; whether and how it scores is a ruleset rule (Part 3) |
| Substitute in the results | Bearman 2024 | Constructor taken from the row. A pair missing from `event_entries` opens an `unknown_driver` or `team_change` review item (HLD §8.2) |
| Provider renames an ID | Possible on any provider update | An unknown ID opens a review item; the admin maps it in `provider_ids` |
| Jolpica and OpenF1 disagree | Possible | Jolpica is primary. A disagreement opens a `provider_mismatch` warning, not a block |
| Same data fetched again | Every finalizer check | No new snapshot; `last_seen_at` and the request log only |
| Duplicate ticks or two workers | Any cron platform can double-fire | `SKIP LOCKED` claim plus unique `dedupe_key` (2.10) |
| Worker dies mid-job | Function timeout or deploy | The lease runs out and the job is retried. Normalizing and scoring are replace-style, so re-running is safe |
| Session times change after jobs were planned | Delays and rescheduling | Pending jobs' `run_at` is updated through `dedupe_key` (2.10) |
| Switching provider mid-season | e.g. Sportradar | A new adapter writes snapshots under its own `provider`. `results` doesn't care where facts came from; `snapshot_id` records it |
| Replaying 2026 for tests | HLD §12 | Snapshots in fetch order plus the simulated clock drive the same pipeline |

**Known limits:**
- If a provider silently changes its JSON shape, the normalizer fails, and the failure is surfaced as a review item and an alert. Only the adapter changes.
- `official_points` is display-only. A rare half-points race comes from the provider as given and doesn't affect fantasy.

### 2.14 Scale
This part barely grows with users, which is the point: provider data is the same whether 50 or 250k people play.

| Foreseeable change | Kind of change |
|---|---|

## Part 3. Fantasy core (proposed)

This part covers the game itself: which rules apply, what can be picked and at what price, and what each team picked and when. Points and standings are Part 4. Everything here is **game data**: it points down at reference data and results, never the other way (0.5).

### 3.0 Official rules this part relies on (re-checked 2026-10-27)
Checked against the official [FAQ](https://fantasy.formula1.com/en/faqs) and [game rules](https://fantasy.formula1.com/en/game-rules). All of this matches HLD §5–6:
- Prices update after each race and stay fixed until the next. They're based on average fantasy performance over the last three Grands Prix, bounded at $3M–$34M.
- Transfers are counted as the net difference from the previous race's lineup, so reverting a change gets the transfer back. One unused transfer carries over, "but must be used then".
- Limitless restores the original team after the race, and a Limitless week carries no free transfer forward.
- **Final Fix:** the outgoing driver keeps points already earned, and the incoming one scores only from the race. If the outgoing driver had Boost, the incoming one gets the 2x. The original team is restored after the race.
- The Wildcard stays active until the next lock.
- **Chip unlocks:** three chips unlock "for your team's 2nd race", the rest are available from the start, and a played chip can't be cancelled.
- If an inactive driver is swapped for the game's suggested replacement, that swap counts toward the transfer allowance.

**Not published officially:**
- **How team value works when you sell.** A fan guide's worked example shows a team's cost cap rising by exactly the price gain of a driver it owns ([FanAmp](https://www.fanamp.com/articles/f1-fantasy-cost-caps-explained)). That matches "buy and sell at the current price, keep unspent money in a bank", which is what 3.6 models. *My call; it mirrors the official game as far as it can be observed.*
- **What a cancelled race does** to chips and transfers. 3.9 sets the rules for this game, confirmed by the owner on 2026-11-07.

### 3.2 `ruleset_versions` and `scoring_rules` (rules as versioned data; decided, HLD §5.6)
**`ruleset_versions`**
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| game_id | uuid FK | |
| version | integer | Unique with `game_id` |
| effective_from_event_id | uuid FK → events | Applies from this event's lock onwards, until a later version takes over. For a correction, the first event it was published for |

**What goes in `params`:** these values are read together, never searched, so `jsonb` fits rule 0.3:
- **Squad:** `squad` drivers 5, constructors 2, boosts 1; `budget` `1000` ($100M); `teamsPerUser` 3.
- **Transfers:** `freePerEvent` 2, `carryOverMax` 1, `penalty` -10, and `carryOverOutInUnlimitedWeek` 0 (what a chip week with unlimited transfers carries forward, 3.8). Transfers are unlimited before the team's first event; that is a rule of the engine, not a param.
- **Chips:** the list of chips. Each has our own name, a stable code, an unlock rule (`from_start` or `after_first_event`) and an effect code the engine knows. The 2026 list:

  | Code | Name | Unlock | Effect |
  |---|---|---|---|

  | `chip_triple_boost` | Overdrive | `from_start` | `triple_boost` |
  | `chip_no_negative` | Safety Car | `from_start` | `no_negative` |
  | `chip_wildcard` | Rebuild | `after_first_event` | `wildcard` |
  | `chip_limitless` | Blank Cheque | `after_first_event` | `limitless` |
  | `chip_final_fix` | Late Call | `after_first_event` | `final_fix` |

- **Window:** `openCutoffHours` 24 and `recheckHours` 6. An event's transfer window opens once the previous event's game event is `final`, or this many hours before this event's lock, whichever comes first; until then the job that opens it looks again every `recheckHours`.
- **Knockout cut-offs:** `knockout` `q2From` 16 and `q3From` 10, for qualifying and sprint qualifying (HLD §5.6).
- **Prices:** `prices` `min` 30 and `max` 340 ($3M–$34M), and `prices.formula`, the constants of the price formula (3.5): `window` 3 events, `pointsPerMillion` for drivers and for constructors (1.0 each), `unscoredPoints` for drivers (6) and constructors (15), `bandSplit` 185 (an asset priced at or above it is expensive), `thresholds` `poor` 0.6, `good` 0.9 and `great` 1.2 (they must rise), and `changes` for `expensive` and `cheap` assets, each four changes in $0.1M for the tiers terrible, poor, good and great (expensive -3, -1, 1, 3; cheap -6, -2, 2, 6). The 2026 values are calibrated (3.5).
- **Abandoned sessions:** `abandonedSessions` is `score_as_classified` (3.9).
- **Autopilot:** `autopilot` `tiebreak` is `original_then_price`. When drivers tie for the highest event points, the original Boost choice stays if it is among them, otherwise the higher-priced driver gets it (4.3).

### 3.5 `asset_prices` and `price_update_runs`
**`asset_prices`:** one row per asset per event.
| Column | Type | Notes |
|---|---|---|
| asset_id | uuid FK → pool_assets | Composite PK with `event_id` |
| event_id | uuid FK | |
| price | integer, units of $0.1M | `CHECK` within 30–340 |
| source | text: `initial`, `formula`, `admin`, `carried` | `carried`: no update ran before this event's lock, so the previous price stands |
| run_id | uuid FK → price_update_runs, nullable | The update that wrote a `formula` price; null for the other sources (`CHECK`: `source = 'formula'` exactly when it is set) |

- **Why one row per event** rather than "price from event X onward": a price list per event is about 33 rows, so a season is under 1,000 rows. Every lookup becomes a direct key read. Each event's prices are fixed from the moment its window opens, so what a team paid can always be explained.
- **Publishing:** when event E is finalized for the game (`finalizeGameEvent`, 4.8), `runPriceUpdate` writes the rows for event E+1 and sets `prices_ready_at`, in the transaction that makes E `final`. E+1's window opens straight after, so builders see the new prices from then on.
- **If prices aren't ready when E+1's window opens,** for example because E is stuck in review past the 24-hour cutoff, E+1 opens on `carried` prices. When E is finalized later, the update skips (`next_open`) and a warning review item `prices_carried` alerts admins. The update is never applied after a window opens.
- **`prices_ready_at` means the list is complete.** Publishing sets it only once every asset available at the event (`active`, added from this event or earlier) has a price for it, so a single admin correction on an unpublished event leaves it null. Carried prices open a window: carrying completes the list, so it writes the `carried` rows and sets `prices_ready_at`, and the window can open on it. It only fills assets with no row for the event, withdrawn ones included, so a price an admin set stays. Running it again writes nothing.
- **A cancelled event's prices stay fixed** (`game_rules_8`): nothing is changed, removed or added there, since the next event carries them (3.9).
- **Fixed when the window opens, by trigger** (decision 1: prices are never applied after a saved team was checked against them). Once an event's game event is `open`, no price for it can be changed or removed. A price can still be added for an asset that has none there, such as a substitute added to the pool for the open event, until it is `locked`, `scored` or `final`; from then nothing can be added either. So admin corrections and the price update go in while the event is `upcoming`, and carrying runs before it opens (the open job carries, then opens). `publishPrices` refuses an open event before writing anything.
- **Admin prices:** a staff price for an event needs a reason and is audited. A mid-season substitute (3.4) gets its `admin` price for its first event in the same transaction, without marking the rest of the list as published.
- **The formula's rows come from `runPriceUpdate`** (`src/game/price-formula.ts`, M4), which `finalizeGameEvent` calls once an event's results are final (4.8). It prices the game's next non-cancelled event by sequence, and only while that event is `upcoming`; otherwise it skips (`next_open`), as it does when the scored event has no current run on any session (`no_scores`) or no event follows (`no_next`). It prices every asset that has a price for the scored event, withdrawn ones included; an asset with none, such as a substitute added since, keeps whatever price it has for the next event. So does an asset whose price for the next event is already `admin`: a price an admin set stays, and its `inputs` entry carries `kept: "admin"` with the formula's figures for the explanation and no change applied. It then publishes through `publishPrices`, which sets `prices_ready_at`. Running it again replaces the rows with a new run.

**`price_update_runs`:** `id`, `game_id`, `after_event_id` (the scored event), `ruleset_version_id` (the version in force for the event being priced, whose formula was used), `inputs` (jsonb: `{ eventId, assets: [...] }`, the event priced and, for every asset priced, its type, the price in force for the scored event, `recentPoints` (oldest first), `average`, `ratio`, `tier`, `change` and `newPrice`, plus `absent` on an asset that missed the scored event), `ran_at`, `ran_by` (text: `system` for the job, or the staff login). Our published formula can then be shown working for every change.

**Formula shape (constants in `prices.formula`, 3.2; calibrated on the 2026 replay):**
1. Average our fantasy points for the asset over its last 3 events (`window`): the newest scored events up to and including the one just scored, each the sum of its `asset_session_totals` over the event's sessions, an asset with no lines in a scored event counting 0. An event it missed (all its lines there are the absent penalties of 4.2) isn't one of them, and when it missed the event just scored, its price stands and there is no tier. Use fewer at the season start or for a newly added asset: an asset's events start at its `added_from_event_id`, placed by sequence as the lineup check places it (`game_event_sequence_from`, so an asset added from a cancelled event starts at the next one), and an event after that with no lines still counts 0. With none, the price stands and there is no tier.
2. Add `unscoredPoints`, then compare that with the points its price "should" earn: `price_in_$M × points_per_million`. Both are separate for drivers and constructors. Prices assume points from categories this game doesn't score, so without this every cheap asset would look terrible.
3. The ratio falls into a tier, and each tier maps to a change scaled by price band: below `thresholds.poor` is terrible, from there to `good` is poor, from there to `great` is good, and `great` or more is great (a ratio on a threshold takes the higher tier). A price of `bandSplit` or more is expensive and uses `changes.expensive`, otherwise `changes.cheap`. For example, a great week is +$0.3M for an expensive asset and +$0.6M for a cheap one.
4. Clamp the result to the version's `prices.min`–`prices.max` ($3M–$34M in 2026; the database check at 30–340 is the backstop). The run's `change` is the tier's change before the clamp.

**Calibration target:** the spread of weekly changes over the replayed 2026 season should look like the official game's.

**Confirmed by the owner (2026-11-07):** `unscoredPoints` and the rule that an absent asset's price stands are this game's rules, not stand-ins until something better.

**Calibration result (2026-11-06, rounds 1 to 19):**
- The official price rule fits a window of 3, thresholds 0.6, 0.9 and 1.2 and these bands: it gives 623 of the 627 weekly moves of active assets. Its zero moves are an asset at $3M or $34M, or an inactive one, whose price stands.
- `unscoredPoints` is what overtakes, Driver of the Day and pit stops earned there per asset per event: 6.0 for drivers and 14.9 for constructors.
- Over the replay, the shares of terrible, poor, good and great are 40, 9, 12 and 37% for cheap assets (official 42, 11, 11, 36) and 16, 13, 11 and 61% for expensive ones (official 16, 14, 16, 55). No move is above $0.6M, as in the official game.

**Corrections after a price update don't change prices** (HLD §5.5). They change points only.

**What the database checks on every save** (a constraint trigger at commit):
- **Window:** for `regular` and `limitless` versions, `app_now() < lock_at` of `for_event_id`, and `for_event_id` is the game's single `open` event. A `final_fix` version is only allowed once the event has locked, after qualifying's results arrive and before the race's scheduled start (`final_fix_window_open`, in `game_rules_7`). **The opening signal is qualifying's `session_result_state` leaving `awaiting`** (M3 decision): nothing sets `sessions.status` to `completed`, and qualifying's scheduled end would let someone swap during a rain-delayed session after seeing Q1. It is the `qualifying` session, not sprint qualifying, so on a sprint weekend the window opens after the sprint. A `final_fix` version applies from the race session, needs Late Call played for the event, and is the locked lineup with one asset swapped: a kept asset keeps its Boost or lack of one, and the incoming asset has the Boost exactly when the outgoing one did. A team has at most one `final_fix` version per event (a partial unique index), so the chip's one swap can't be repeated.
- **Chips:** a `limitless` version needs Blank Cheque played for its event, and with the x3 Boost played its target must stay in the lineup as a driver without the 2x Boost (3.9).
- **Composition:** squad counts per type, and one Boost on a driver, all read from ruleset params.
- **Assets:** active, or already owned in the base lineup if withdrawn.
- **Budget:** the cost at this event's prices fits within the team's purchasing power (3.8). A `limitless` version skips this check.
- **Only complete lineups can be saved.** Drafts live in the browser. That removes the "half a team at lock" case entirely.

**The clock function (`app_now()`).** It returns `now()` in production. On a replay branch, where a `simulated_clock` setting exists, it returns the simulated time. This keeps HLD rule 6 (one injectable clock) true inside the database too. A production database never has the setting. **Decided 2026-10-28 (HLD decision 20):** application SQL takes `$now` from the entry point's clock, and `app_now()` is the backstop inside triggers. In replay, the entry point reads `app_now()` once, so both see the same instant.

**The locked lineup for event E** is the latest `regular` or `limitless` version for E with `saved_at < lock_at`. If there's none, it's the team's base lineup carried forward. It's deterministic, so it can be recomputed at any time with the same answer (HLD §3.3 rule 3).

**Pruning:** versions that never became a locked lineup are deleted 7 days after the event is final, keeping the last one before lock. Locked versions are kept forever.

**As built** (`pruneLineupVersions`, `src/game/corrections.ts`, run by the daily `game_checks` job, 4.8): a version goes when its `for_event_id` has a game event that is `final` with `updated_at` 7 days ago or more (a later update, such as a correction, only delays it). It stays if any lock record points to it as `base_version_id`, `locked_version_id` or `final_fix_version_id`, or if it is the team's newest for the event by `(saved_at, id)`: the last one before lock for a team with no lock record, and what `saveLineup` compares against as the team's latest. A kept version based on a deleted one has its `based_on_version_id` nulled.

### 3.8 Transfers, team value and the per-event lock record
**`team_event_states`:** one row per team per event it took part in, written by the lock job.
| Column | Type | Notes |
|---|---|---|
| team_id, event_id | composite PK | |
| game_id | uuid FK | |
| base_version_id | uuid FK, nullable | The lineup compared against: the previous event's locked `regular` lineup, or the pre-Limitless one. Null at the team's first event |
| locked_version_id | uuid FK | What counts for this event |
| final_fix_version_id | uuid FK, nullable | |
| chip_play_id | uuid FK, nullable | The chip played for the event: set by the lock job, or by a Late Call after the lock (with `final_fix_version_id`). A trigger checks that both point at the row's own team and event, and that `final_fix_version_id` is a `final_fix` version |
| is_first_event | boolean | |
| purchasing_power | integer | Money available at this event's prices |
| spent | integer | Cost of the locked lineup at this event's prices |
| bank | integer | `purchasing_power - spent`, never below 0 (except Limitless) |
| transfers_made | integer | Net count: assets in the locked lineup that aren't in the base (all of them at the first event, which has none) |
| free_transfers | integer | Allowance this event, including carry-over in, or "unlimited" (null) |
| carry_over_out | smallint | 0 or 1 |
| transfer_penalty | integer | Copied into the ledger as its own line (Part 4) |
| ruleset_version_id | uuid FK | |

**Team value (my call, mirroring the official game):** every asset is bought and sold at its **current** price, and unspent money stays in the bank.
- First event: `purchasing_power = budget` ($100M).
- After that: `purchasing_power(E) = bank(base event) + the base lineup's assets at E's prices`.

So price rises of owned assets raise a team's value, and falls lower it. **Keeping an unchanged lineup is always affordable**, because that sum is exactly the base lineup's cost plus a bank that's never negative.

**Two SQL functions hold this (in `game_rules_5`), so the sum is made in one place:**
- `team_base_state(team_id, event_id)` returns `base_version_id`, `bank`, `carry_in` and `is_first`, from the team's latest row before the event by `game_events.sequence`. With no such row it's the team's first event (no base, no bank). When that row was a Limitless week (its `chip_play_id` is a played chip whose effect is `limitless`, since `game_rules_7`; whatever kind of version locked), it returns that row's own base, the bank of the row before it, and a `carry_in` of 0.
- `team_purchasing_power(team_id, event_id)` is the ruleset's `budget` at a first event, otherwise `bank` plus the base lineup's assets at the event's prices. An owned asset with no price at the event is an error, never 0.

The save check calls `team_purchasing_power` for every version except `limitless` (refused as `over_budget`), and the lock job calls both to write the row. A withdrawn asset passes the save check only while it's in `base_version_id`, so owners keep it at its carried price and get that price back when they sell, but can't buy it back once the sale has locked. **The bank is never below 0 outside Limitless:** a CHECK can't see the chip, so the lock job asserts it and fails loudly if it's broken.

**Chip weeks:**
- **Limitless:** budget not checked, transfers unlimited, no carry-over out. The next event's base is the **pre-Limitless** lineup, with that lineup's bank, so the team "reverts" automatically. The next event's purchasing power uses current prices for the restored team.
- **Wildcard:** transfers unlimited and free, but the budget still applies. It stays playable until lock, and the result becomes the new base. Carry-over out in a Wildcard week follows a ruleset param. *Proposed: 0, the same as Limitless.* Official text only says this for Limitless, so it's my call.
- **Final Fix:** one asset swap, checked against this event's purchasing power. It's free. The next event's base is the **locked** (pre-Final-Fix) lineup.

**Carry-over:** `carry_over_out = min(carryOverMax, free_transfers - transfers_made)`, never below 0 (`carryOverMax` is 1). That keeps "one transfer carries over but must be used then": two unused don't become two carried. In a week with unlimited transfers (`free_transfers` null: the team's first event, Wildcard or Limitless) it's the ruleset param `carryOverOutInUnlimitedWeek` instead, 0 for 2026, and there's no penalty. Otherwise `transfer_penalty = penalty × max(0, transfers_made - free_transfers)`. These are pure functions in `src/game/transfers.ts`, pinned by tests.

**Lock correctness doesn't depend on the lock job.** If the job is late, the row can be computed afterwards from versions, prices and chip plays with the same result: it reads only versions for the event saved before `lock_at`, the event's prices and the team's earlier rows, so a late run writes what an on-time one would. Events lock in order and the next one can't open until this one has locked (3.3), so a team's earlier rows are always there: "no earlier row" really means the team's first event. The job (`lockEvent`) works in batches of about 1,000 `active` teams in id order, inserts each row or leaves one already there, sets `teams.first_event_id` on a team's first row, and on the last batch sets the event `locked` and the game `running`. A team created after lock gets no row for that event and starts at the next one (decided, HLD §5.2), and so does a team that never saved; a retired team gets no row.

| chip_code | text | Must exist in the event's ruleset params |

| target_asset_id | uuid FK, nullable | The x3 Boost driver: a driver in the team's lineup and not the 2x Boost one. Only that chip has one |
| played_at | timestamptz | From `app_now()` |
| status | text: `played`, `refunded` | No delete and no undo (verified rule). Only the system refunds, for a cancelled event |

- **Constraints:** unique `(team_id, chip_code) WHERE status = 'played'` gives once per season. Unique `(team_id, event_id) WHERE status = 'played'` gives one chip per race.
- **Timing:** a constraint trigger at commit (`game_rules_7`) checks that the code is in the event's ruleset params, the play window (before lock on the game's open event, or the Final Fix window of 3.7, by the same clock as a save) and the unlock rule: an `after_first_event` chip only at an event later, by sequence, than `teams.first_event_id`.
- **No undo:** a trigger refuses a delete (except the cascade from a team deleted outright before its first lock) and every update except `played` to `refunded`, which it allows only for a `cancelled` event. A refund is final.
- **Where the x3 Boost target is checked (M3 decision):** when the chip is played (the target is a driver in the team's latest lineup for the event, or its base, without the 2x Boost) and **on every save** after it (a lineup that drops the target or puts the 2x Boost on it is refused as `composition`), not at lock, where it is too late to refuse anything. The lock job only asserts the rule held, and fails loudly if it's broken.
- **Effects M3 enforces:** Wildcard and Limitless make the week's transfers unlimited (`free_transfers` null, no carry-over out); Limitless saves `limitless` versions, which skip the budget, and the next base reverts (3.8). Late Call is one call (`saveFinalFix`) that plays the chip, saves the `final_fix` version and sets the event's `final_fix_version_id` and `chip_play_id`. The points effects (Strategist, the x3 Boost, Safety Car) are M4's.

**Cancelled events (my calls, check these):**
- **Cancelled before lock:** nothing locks. Chips played for it are **refunded**. There's no `team_event_states` row, so the next event's transfers are counted against the last real locked lineup, and no extra free transfers are granted. Prices don't change: the next event, if it has no prices yet, carries the cancelled event's list.
- **Lineups saved for it still count (decided for M3):** an event cancelled while its window is open doesn't undo what teams saved for it. At the next event's lock, a team that saved nothing for that event locks its latest `regular` version saved for a cancelled event since the previous event's lock (`team_locked_lineup`, in `game_rules_8`; the lock job and the x3 Boost check both read it), and only then its base. A `limitless` version doesn't carry, since its chip was refunded. A team whose first lineup was saved for the cancelled event starts at the next one. A refunded Rebuild (Wildcard) refunds the chip, not the transfers: a lineup saved under it counts as normal transfers at the next lock, whose window opens at once.
- **In one transaction** (`planGameEvents`, which the calendar sync runs for each game before planning its jobs): the game event becomes `cancelled` with no sequence, its chips are refunded, and if it was the open event, the next upcoming one opens at once (prices carried first when none were published).
- **"Before lock" means before the lock has started:** once an event's `lock_at` has passed, or the lock job has written any of its rows, its game event is never cancelled or renumbered, whatever its status. The lock job finishes, and the event is treated as cancelled after lock.
- **Session cancelled after lock** (e.g. a race called off after qualifying): sessions already run stay scored, and the cancelled session simply has no results. Chips stay used, because the lock happened. Prices update as normal from what was scored. A game event that has locked never becomes `cancelled`, even if its event does: it keeps its sequence, its lock record and its chips.
- **Event cancelled after lock:** the event's own finalize check does nothing for a cancelled event, so the daily `game_finalize` sweep (4.8) closes it for the game. The game event becomes `final` on what was scored, so its totals and standings are `final` and the next event's prices come from the formula. With nothing scored, the update skips (`no_scores`), the game event still becomes `final`, its lock records get totals of 0, and the next window opens at once on carried prices, not at the 24-hour cutoff. **Transfer penalties (decided 2026-11-07):** an event that scored nothing applies none, since its totals are 0; one where any session scored applies them as normal. A session that was under review stays as it is: it holds nothing here, since no check will ever finalize its results.

**Abandoned sessions with a classification** (e.g. Belgium 2021): scored as classified by default (ruleset param). Admins can void one through `game_session_exceptions` (`setSessionException`, policy `skip`), and clear it again (`clearSessionException`, which removes the row). Both need a reason and are audited, and both trigger a re-score (M4). A session has at most one exception per game. `decided_by` is a `users` FK; the system user until staff have accounts, and the audit row names who acted.

This part turns effective results (Part 2) and locked lineups (Part 3) into points, totals, ranks and league tables. Every point must be explainable line by line (HLD §1). Every number here can also be **rebuilt from its inputs** (0.7), so a bug or correction is a re-run, never a hand repair.

### 4.0 The ledger's shape (decided principle; storage choice is my call)
The HLD fixed the principle: a two-tier ledger, with asset score lines computed once and shared, plus team lines on top (HLD §5.6). What remained was **how much of the team tier to store**. At the "big" size of 250k teams there are about 30 team lines per team per event, which makes it decisive:

| Option | What's stored per team | Rows per season at 250k teams | Trade-off |
|---|---|---|---|
| A. Store every team line | base points per asset per session, plus boosts, chips and penalties | ~180M | Simplest to read, but the biggest table in the system by far. Every re-score rewrites millions of rows |
| B. Store only totals | totals; the breakdown is recomputed by the engine on demand | ~6M | Smallest, but a breakdown depends on today's engine code matching the code that produced the total. That's harder to trust after a bug fix |
| **C. Store only what's team-specific (chosen)** | Boost, chips and penalties as stored lines. **Base lines are a SQL view**: the locked lineup joined to the shared asset lines | ~30M | Every line is still visible and adds up exactly. Base lines can't drift from asset scores because they *are* asset scores. A re-score rewrites about a sixth of option A's rows |

**Option C** keeps the HLD's promise (boosts and chips as separate lines; every point explainable) at a fraction of the cost, and stays comfortably inside the free tier at beta size. *My call; it settles the open "proposed" item in HLD §5.6.*

### 4.1 `scoring_runs` (every scoring attempt, and which one counts)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| game_id | uuid FK | |
| session_id | uuid FK | Scoring is per session (delete and replace; decided, HLD §5.6) |
| ruleset_version_id | uuid FK | |
| engine_version | text | The scoring code's version, `ENGINE_VERSION` in `src/scoring/engine.ts` (`2026.1`). A bug fix bumps it |
| input_fingerprint | text | SHA-256 of everything read: the effective results, the session exception, the ruleset version with its rules and knockout params, the pool at the event and the engine version. **If it matches the current run's fingerprint, a live run is skipped**, which makes re-triggering free |
| trigger | text: `results`, `override`, `exception`, `ruleset_correction`, `engine_change`, `admin`, `replay` | |
| mode | text: `live`, `dry_run` | `dry_run` computes and reports differences without writing (4.9) |
| status | text: `running`, `succeeded`, `failed`, `superseded` | |
| is_current | boolean, default false | **Partial unique index: at most one current run per `(game_id, session_id)`**. Only a `live` run can be current (`CHECK`) |
| inputs | jsonb, nullable | `{ results, exception }`: the effective results rows exactly as read (every column, by driver id), about 22 rows, and the session exception (`policy`, `reason`) or null. That's what the score explanation cites, even if results change later. Null until the run writes its lines |
| diff_summary | jsonb, nullable | `{ previousRunId, assetsChanged, teamsChanged, biggest, assets }`: counts of assets and teams whose points changed versus what was last published (the latest `succeeded` live run, `previousRunId`; for a team, its `team_event_totals.points` for the event, 0 with no row), the 10 biggest changes (`{ kind: "asset" \| "team", id, before, after, change }`, by size), and every changed asset's session points before and after. This feeds admin review and correction notices |
| started_at, finished_at | timestamptz | From the caller's `now`. `finished_at` is set when the run succeeds, fails or is superseded |

**Concurrency:** if a second run starts while one is in flight for the same session (two corrections a minute apart), the later run wins. Each write step checks that its run is still the newest started one and stops if not, marking itself `superseded`. Two runs never interleave their writes.

**As built** (`src/game/scoring-runs.ts`; each step is one transaction, so a job can run them one at a time, 4.8):
- **`startRun`** reads the inputs and fingerprints them (`inputFingerprint`): the canonical JSON (object keys sorted at every depth, and the results, rules and pool sorted by driver, code and asset ID, so neither row nor key order can change it), hashed with SHA-256. The fingerprint covers **every column read from `effective_results`**, `snapshot_id` included, so a new snapshot with identical rows re-scores, with an empty diff. A `live` run is skipped, writing nothing, only when its fingerprint equals the current run's, that run has `succeeded`, and no newer live run for the session is still `running` (it may yet write what it read). The check and the insert are one transaction under the event's ledger lock, so a `writeAssetLines` in flight commits first and is seen. `force` skips the check, for a re-score an admin asks for. The new run is `running`. Only `qualifying`, `sprint` and `race` sessions score (the engine's kinds), and only in a game event that is `locked`, `scored` or `final`.
- **`writeAssetLines`** reads the inputs again and scores them, so `inputs`, the fingerprint and the lines always agree. It replaces the session's lines and makes the run current (4.2), and computes the assets part of `diff_summary` against the lines it replaces, unless the run it replaces never finished (superseded, `failed` or stopped mid-way): then its lines were never published, so each asset's `before` is the one that run recorded in its own `diff_summary.assets` where listed (an asset it didn't list is unchanged from the published figure, so its lines are right), and a chain of such runs reaches back to the published figure. A `dry_run` stores its inputs and diff, but writes no lines and never becomes current.
- **`writeTeamAdjustments`** writes the team lines in batches (4.3) and adds each team whose event points changed to `diff_summary`: its new event points (base plus adjustments) against its `team_event_totals.points` for the event (0 with no row), which only a finished run moves (its job recomputes the totals, 4.8). A batch run again (a retried job) writes the same lines and counts no team twice.
- **`finishRun`** marks the run `succeeded`, with `finished_at` and the final `diff_summary`.
- **A step that throws leaves its run `running`:** its transaction rolls back, and the queue retries the job. Each step is safe to run again. If it throws on the job's last attempt, the handler marks the run `failed` (`failRun`, only while it is still `running`) and the job goes `dead`, which alerts admins. A failed run's lines stay until the next run replaces them, and a failed current run is never skipped against. A worker that dies on the last attempt never gets that far: `reapExpired` dead-letters the job and the run stays `running`, which the daily recovery picks up (4.8).
- **A new live run supersedes the earlier ones:** `startRun` marks every earlier `running` live run of the session `superseded` in the transaction that inserts the new run, so a retried first step can't leave its first run `running` for ever. A dry run doesn't, and isn't touched by one.
- **A dry run** (`dryRunGame`, 4.9) is started with `startRun` and scores through `writeAssetLines`' own step. `writeTeamAdjustments` refuses one: `dryRunEvent` works out its teams in memory, through the code a live run uses.
- **The newest started run** is the one with the highest ID (UUIDv7) of the **same mode** for the game and session, so a dry run never supersedes a live one. Every write step first takes the event's ledger lock (`pg_advisory_xact_lock` on the game and event) and then checks for a newer run. The asset lines of an event's sessions and its team lines are therefore written by one step at a time, and a batch never mixes two runs' asset lines.

### 4.2 `asset_score_lines` (tier 1: shared by every team)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| game_id, session_id | uuid FKs | |
| run_id | uuid FK → scoring_runs | |
| asset_id | uuid FK → pool_assets | |
| rule_code | text | From `scoring_rules.code` (3.2) |
| category | text | Copied from the rule, for No Negative |
| subject_driver_id | uuid FK → drivers, nullable | For a constructor's aggregate lines: **which driver's points these are**. This can be a driver **who isn't in the pool**, such as a substitute (HLD §8.1) |
| points | integer | |
| detail | jsonb | For the explanation only, e.g. `{ "from": 7, "to": 3 }` or `{ "position": 2 }` |

- **Unique `(game_id, session_id, asset_id, rule_code, coalesce(subject_driver_id, nil))`** (`asset_score_lines_line_unique`).
- **How a constructor's aggregate is built:** the engine scores **every driver in the results**, not only pool drivers. A constructor's aggregate lines then sum the drivers whose result rows name that constructor in that session (1.9).
- **Only pool assets get rows.** A non-pool driver's points exist only inside the constructor aggregate that used them.
- **Inactive pool drivers get their penalty lines** even with no result row. The engine iterates the pool, not the results (HLD §6).
- **Re-scoring a session** deletes its lines and inserts the new set in one transaction, tagged with the new `run_id` (HLD §5.6). A session with a `skip` exception (3.3) gets no lines.
- **The pool at the event** is every asset added from that event or an earlier one, placed by sequence as the lineup check places it (`game_event_sequence_from`), withdrawn ones included (3.4).

**`asset_session_totals`** is a view (`ledger_rules` migration): `(game_id, session_id, asset_id, points, by_category)`, the points per asset per session, with `by_category` the per-category subtotals as a JSON object. A category's subtotal is every line of that category, so a constructor's adds both its drivers' copied lines together, and No Negative floors that combined subtotal. An asset with no lines has no row. Team math and the price formula read it.

### 4.3 `team_adjustment_lines` (tier 2: what's specific to a team)
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| game_id, team_id, event_id | uuid FKs | |
| session_id | uuid FK, nullable | Null for event-level lines, such as the transfer penalty or the Autopilot move |
| asset_id | uuid FK, nullable | The asset the line is about |
| line_type | text: `boost`, `triple_boost`, `autopilot_remove`, `autopilot_add`, `no_negative`, `transfer_penalty` | Each is a separate visible line (decided) |
| category | text, nullable | For `no_negative`: which category was floored |
| points | integer | e.g. Boost = +1× the asset's session points, x3 = +2×, No Negative = the amount added back |
| run_id | uuid FK | The scoring run that last wrote it |

**`team_base_lines`** is a view (`ledger_rules` migration, rebuilt in `base_lines_filter_early`), and needs no storage: `(game_id, team_id, event_id, session_id, asset_id, points)`. For each lock record (`team_event_states`), session of its event and asset in that session's effective lineup with lines in `asset_score_lines`, it gives the asset's session points. The **effective lineup** is the locked version (`locked_version_id`), or the Final Fix version (`final_fix_version_id`) from the session it applies from, the race, onward, by `(scheduled_start, id)`: the order `effectiveLineup` uses (3.7). Each row sums the asset's own lines for the session, so base lines can't disagree with asset scores (`asset_session_totals` sums the same lines), a read costs only the teams it asks for, and an asset with no lines has no row.

**Writing the lines** (`writeTeamAdjustments`): the teams with a lock record for the event, in ID order, about 1,000 per transaction. For each, `teamAdjustments` (`src/game/adjustments.ts`) runs over every scored session of the event (those with a current run), from `asset_session_totals`, the lock record (the locked and Final Fix versions, the chip played and `transfer_penalty`) and the event's prices. The team's lines for the **whole event** are deleted and the new set inserted, tagged with the run. A lock record whose `chip_play_id` doesn't match the team's played chip fails the batch.

**A team's score explanation** is `team_base_lines` plus `team_adjustment_lines` for that team and event, and the two always add up to the stored total (4.4). A nightly check compares them for a sample of teams, and any mismatch alerts admins and triggers a rebuild.

**How adjustments are calculated (proposed):**
- **Boost:** +1× the boosted driver's session points, per session. After a Final Fix, the incoming driver gets it from the race (verified rule).
- **x3 Boost:** +2× the target's points. The 2x Boost still applies to its own, different driver.
- **Autopilot:** after each scored session, it recomputes which driver has the highest event points so far, and moves the Boost there with a remove/add pair. It's provisional until the event is final. **Ties: the original Boost choice stays if it's among the tied drivers; otherwise the higher-priced driver gets it** (my call; a ruleset param).
- **No Negative:** for each owned asset and each scoring category with a negative subtotal, a line adds back exactly that amount. **Transfer penalties still apply** (verified rule).
- **Transfer penalty:** copied from `team_event_states.transfer_penalty` (3.8), as one event-level line.

### 4.4 `team_event_totals` (totals, running totals and ranks)
| Column | Type | Notes |
|---|---|---|
| game_id, team_id, event_id | composite PK (team, event) | |
| event_sequence | integer | From `game_events.sequence` (3.3) |
| points | integer | This event: base plus adjustments |
| points_by_session | jsonb | `{session_id: points}` for the event's scored sessions. **Spoiler control:** show only the sessions a user has watched (HLD §7.3), without extra rows |
| cumulative_points | integer | The season running total through this event |
| first_reached_sequence | integer | The earliest event sequence at which the running total was **at least** today's `cumulative_points`. **This is the tiebreak** (decided: earliest to reach) |
| global_rank | integer | Rank in the game through this event. Ties on points and `first_reached_sequence` share a rank (decided) |
| status | text: `provisional`, `final` | Follows the event (2.3) |
| computed_at | timestamptz | |

- **One row per team per event it took part in.** A team that joined later has no rows for earlier events. A cancelled event has no rows, and the next event's running total simply carries on.
- **`first_reached_sequence`** is computed with a window over the team's running totals. The running total can go down (negative weeks), so it's "first time at or above", not "first time equal".
- **Indexes:** `(game_id, event_id, global_rank)` for the leaderboard, and `(team_id, event_sequence)` for a team's history.

**Built (M4)** as `recomputeTotals(db, now, { gameId, fromEventId })` (`src/game/totals.ts`), in set-based SQL: one statement per call, in one transaction, however many teams there are. It returns `{ events, teams }`: the events whose running totals were recomputed and the teams written for `fromEventId`.
- **The event's rows** are one per team with a lock record (`team_event_states`) for `fromEventId`. `points` is the sum of the team's `team_base_lines` for the event plus the sum of its `team_adjustment_lines` for it, event-level lines included (the transfer penalty). `points_by_session` has an entry for each scored session (one with a current run), base plus that session's adjustments, so an event-level line is in `points` and in no session, and the sessions can add up to less than the total. A row whose lock record is gone is deleted.
- **The running total** at an event is the team's `points` summed over its rows at that sequence or earlier. A cancelled event has no sequence and no rows, so nothing is skipped over.
- **`first_reached_sequence`** is the smallest sequence among the team's rows, up to and including this one, whose running total is at or above this one's (so a total of 50, 40, 50 has 1, 1, 1).
- **`global_rank`** is `rank()` over all the game's rows at the event, ordered by `cumulative_points desc, first_reached_sequence asc`, so ties share a rank and the next rank skips.
- **A rebuild reaches forward.** Running totals, firsts, ranks and `status` are rewritten for `fromEventId` and every later event with rows, but only `fromEventId`'s `points` are recomputed. A correction to an early event moves the standings after it and leaves what each later event scored. A later row is only updated if one of those changed, so its `computed_at` is when it last changed. Each event's own scoring recomputes from it, so a later event's `points` are always as of its last run.
- **`status`** is `final` once the game event is `final`, and `provisional` before.
- **Locking:** the event's ledger lock (the one each scoring step takes), then a lock on the game's totals, since a rebuild writes later events' rows and two rebuilds of one game take turns whichever event they start from. The ledger lock is taken per step, in that step's own transaction: it stops a rebuild interleaving with a single step, not with a run, so a rebuild between a run's steps can see new base lines next to old adjustment lines. A run's totals are right once its totals step (step 3 of 4.8) recomputes after the last team batch. One `fromEventId` per transaction: two events in one transaction can deadlock against a step.
- **Checks:** `first_reached_sequence` is between 1 and `event_sequence`, and `global_rank` is at least 1.

- **Unique per auto league:** `(game_id, kind, constructor_id)` and its driver and country equivalents. There's exactly one "Ferrari fans" league per game.
- **Auto leagues are keyed by constructor ID, not name,** so a rebrand doesn't split a league (1.7).
- **A mini-league range uses event sequences, not rounds, and it stays on the same real events (decided 2026-11-07).** Sequences can move before an event locks (3.3), so `planGameEvents` moves every range with them in the same transaction (`moveLeagueRanges`, `src/leagues/ranges.ts`). A start on an event cancelled before its lock moves forward to the next race, and an end moves back to the race before it. An event cancelled after its lock keeps its sequence, so a range on it stays. A league left with no races moves to the next one. With nothing after it, the range stays where it is and covers nothing, so the league has no table, because moving back onto a scored race would build none; a race reinstated there is covered again (*my call for these last two cases; check them*). A whole-season league has nothing to move.

**Built (M4)** in `src/db/schema/leagues.ts`, with `createLeague` and `syncAutoLeagues` in `src/leagues/leagues.ts`.
- **`createGame` makes the game's `global` league** in the same transaction (name "Global", slug `global`). A partial unique index allows one per game. It has no code, owner, limit or range of its own, and no members.
- **`CHECK`s:** the `auto_*` kind has exactly its own key, and the other kinds have none; only `public` and `private` leagues have an owner, a code, a limit and a range other than the whole season; a user league's name is 1 to 40 characters; `start_sequence` is at least 1 and `end_sequence` is not before it; `max_members` is at least 1. `slug` is unique per game, and `owner_user_id` is a `users` FK (`ON DELETE RESTRICT`).
- **`createLeague`** makes a `public` or `private` league and returns `{ leagueId, joinCode }`. **Both kinds get a code,** so a public league can be shared too; only the code joins a league (there is no browsing here). The code is 10 characters of `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no I, L, O, 0 or 1) from `crypto.getRandomValues`, with bytes that would skew the pick thrown away. The slug is the name plus a random suffix, **not** part of the code, so a private league's code can't be read off its URL. A collision on the code or slug is retried (up to 5 times). A bad name is `bad_name`.
- **`syncAutoLeagues`** takes a user, a game and the profile's constructor ID, driver ID and country code. For each key that isn't null it finds the game's league for the key or creates it ("Ferrari fans", slug `constructor-ferrari`), and moves every **active** team of the user in that game in. A team leaves the auto leagues of the same kind that don't match, and a null key means none of that kind. Memberships are `auto`, stamped with the `now` it was given. It is idempotent, and one user's syncs take turns (an advisory lock). A team created later is moved in by running it again.

### 4.6 `league_memberships`
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | |
| league_id | uuid FK | |
| team_id | uuid FK | Must belong to the league's game (trigger) |
| joined_at, left_at | timestamptz | Leaving sets `left_at` and rejoining makes a new row, so there's history |
| source | text: `user`, `auto` | `auto` covers the global, constructor, driver and country leagues |

- **A team is in a league at most once at a time:** unique `(league_id, team_id) WHERE left_at IS NULL`.
- **The soft cap of 50 leagues per team** (decided) is a trigger, and it counts `user` memberships only.
- **Auto memberships follow the profile.** If a user changes their favorite team or country, the team leaves the old auto league and joins the new one.
- **A league ranks its members' totals over the league's range, regardless of when they joined.** That's how the official mini-leagues work: only the selected races count.
- **The global league has no membership rows.** Every active team is in it by definition, and its ranks are `team_event_totals.global_rank`. That saves 250k rows per game.

**Built (M4)**, with `joinLeague` and `leaveLeague` in `src/leagues/leagues.ts` and the rules in the `league_rules` migration.
- **The cap is per team, not per user:** 50 current `user` memberships for one team (this one counted), as the index on `(team_id) WHERE left_at IS NULL` suggests. A user with 3 teams can have 150 memberships in all. Auto memberships don't count. The trigger takes a lock per team, so two joins at once can't both take the 50th place. It raises **GL008**, which the game layer maps to `league_cap`.
- **The same trigger checks** that the team belongs to the league's game, that the league isn't the `global` one, and that the source fits the kind (`user` for a public or private league, `auto` for an auto one). These are plain check violations; `joinLeague` finds a code from another game's league as `league_not_found` first.
- **`joinLeague({ joinCode, teamId, userId })`** (the code in any case, trimmed) refuses with, in this order: `team_not_owned` (the team isn't `userId`'s, or doesn't exist), `team_retired` (a retired team holds no place in a league, so it can't join), `league_not_found` (no active public or private league has that code, or it's another game's; auto and global leagues have no code, so they can't be joined by hand), `already_member` (a current membership; the unique index says the same to anything that skips the check), `league_full` (current members whose team is active at `max_members`: a retired member holds no seat) and `league_cap`. The league row is locked while it joins, so a limit holds under concurrent joins.
- **`leaveLeague({ leagueId, teamId, userId })`** sets `left_at`. A league that isn't public or private (auto leagues follow the profile) or one the team isn't in is `league_not_found`; a team that isn't `userId`'s is `team_not_owned`. Rejoining is a new row.
- **Deleting a team** that never locked (`removeTeam`) deletes its memberships and standings with it (`ON DELETE CASCADE`). A retired team keeps both.

### 4.7 `league_standings` (current table for each league; replaced after each scoring run)
| Column | Type | Notes |
|---|---|---|
| league_id, team_id | composite PK | |
| points | integer | Over the league's range |
| first_reached_sequence | integer | The tiebreak, computed **within the league's range** (decided) |
| rank | integer | Shared on a full tie |
| previous_rank | integer, nullable | For the "up 3" arrows |
| through_event_id | uuid FK | |
| status | text: `provisional`, `final` | |

- **Only the current table is stored.** Rank history for one team in one league is computed on demand from `team_event_totals`. That's cheap for one league, and saves storing every league's table for every event.
- **Retired teams** (3.6) stop scoring and are dropped from league tables. Their past `team_event_totals` stay.
- **Index:** `(league_id, rank)` for paged tables, including a 100k-team public league.

**Built (M4)** as `recomputeStandings(db, now, { gameId, eventId })` (`src/leagues/standings.ts`), in set-based SQL: one statement for all the leagues, in one transaction (with a lock on the game's standings, so two rebuilds take turns). It returns `{ leagues }`: the leagues rebuilt.
- **Which leagues:** every `active` league of the game except `global` whose range (`start_sequence` to `end_sequence`, null for no end) includes the sequence of `eventId`. Another league's table isn't touched. The table runs through the latest event in the range that has totals (`through_event_id`); a league with none is emptied.
- **Who is in it:** current members (`left_at` null) whose team is `active`. A team that left, or retired, has no row. A team with no totals in the range has none either, until its first event is scored.
- **`points`** is the sum of the member team's `team_event_totals.points` for the events in the range, whenever it joined: a member who joined late ranks on the whole range.
- **`first_reached_sequence`** is the earliest sequence in the range at which the team's running total **over the range** was at least its total now, so a league starting at event 5 ignores what the team scored before it. **`rank`** is `rank()` over the league by points descending, then that, so a full tie shares a rank and the next one skips.
- **`previous_rank`** is the team's rank in the table this one replaces, when that table ran through a different event. A rebuild through the same event (a correction, or a run again) keeps the `previous_rank` the row had, so the arrow shows the move since the last event. A team that wasn't in the old table has none.
- **`status`** is `final` once the through event is `final`, otherwise `provisional`.
- **Paging:** both `ORDER BY rank LIMIT n OFFSET m` and `rank > last ORDER BY rank LIMIT n` read `(league_id, rank)` with no sort (checked with `EXPLAIN`). For a deep page prefer the second.

### 4.8 What happens after results change (the scoring pipeline)
Each step is a job (2.10) keyed by the run ID, so a re-run is safe and a superseded run stops early:
1. **Score the session:** replace the asset lines (4.2).
2. **Recompute team adjustments for the event:** done for all teams in batches of about 1,000, in set-based SQL. Boost amounts, Autopilot and No Negative depend on asset points, so all of them are recomputed.
3. **Recompute `team_event_totals`** for that event, then the running totals and ranks for that event **and every later one**, since a correction to an old event moves everything after it.
4. **Recompute `league_standings`** for leagues whose range includes the event.
5. **Notify:** "provisional scores are in", or for a correction, "your score changed by +3 (stewards' decision)". Spoiler-safe wording, batched (2.10). *Not built yet: steps 1-4 are.*

**As built** (`src/game/score-jobs.ts`):

**What queues a run.** `enqueueScoring(db, now, { sessionId, stamp, trigger, gameId? })` queues one `score_session` job per `running` game whose game event for the session's event is `locked`, `scored` or `final`, and returns how many it queued. It queues nothing for a cancelled session, a kind the engine doesn't score, or a session whose result status isn't `provisional` or `final`.
- **The results hooks** call it after every `advanceStatus`, with the stamp `v<resultsVersion>`: the poll and finalize jobs with the trigger `results`, and `revalidateEvent` (so overrides too) with `override`. The key is `score:<gameId>:<sessionId>:v<resultsVersion>`, so the same version queues one job however many checks see it. The season import doesn't call it: a backfill scores nothing.
- **A session exception** set or cleared calls it in the audit's transaction, for that game only, with the trigger `exception` and the key `score:<gameId>:<sessionId>:x:<auditId>`.
- **A correction** (4.9) calls it the same way, with the trigger `ruleset_correction` and the stamp `c:<auditId>`, and an **approved re-score** with `engine_change`, the stamp `r:<auditId>` and `force`, which the `assets` step passes to `startRun`.
- **The daily recovery** (`game_checks`, below) calls it for one game, with the failed run's own trigger, the stamp `retry:<yyyy-mm-dd>` and `force`.
- **A session under review queues nothing.** Resolving its item doesn't move the status; the next `finalize_check` or revalidate does, its version goes up, and that call queues the run.

**`score_session`** runs one step per job, and queues the next under `score:<runId>:<step>:<afterTeamId|start>`:
- `assets`: `startRun` then `writeAssetLines`. A skip (the same fingerprint as the current run) ends the chain there, with nothing else run. It also stops for a session that was cancelled or has gone back under review since it was queued.
- `teams`: one `writeTeamAdjustments` batch, then the next batch or `standings`. Totals aren't touched here: the ledger lock doesn't span a run, so they're only right after the last batch.
- `standings`: `recomputeTotals` from the event, `recomputeStandings`, then one transaction that runs `finishRun` and moves a `locked` game event to **`scored`**. A superseded run doesn't move it.

`teams` and `standings` stop quietly for a run that isn't `running`, which is what a job run twice finds. Any step stops quietly when the game event is cancelled or hasn't locked. `global` leagues have no standings rows: their ranks are `global_rank` (4.4).

**`game_finalize`.** When the finalize job marks an event `completed`, it queues `game_finalize:<gameId>:<eventId>` in that transaction, for each `running` game whose game event is `locked` or `scored`. The job runs `finalizeGameEvent(db, now, { gameId, eventId })`, which returns quietly unless the game event is `locked` or `scored`, then:
1. **Outside any transaction**, since runs are batched: each scored session of the event that isn't cancelled and whose result status is `provisional` or `final` gets `startRun` with the trigger `results`, and any run that isn't skipped goes through its steps inline. A session with no results gets no run: one would write absent-driver penalties. A superseded run just stops, since the newer run's chain owns the session.
2. **One transaction**, ledger lock first (so the order is ledger then `game_events` row, as in the `standings` step, and the two can't deadlock). It reads the status again under that lock, holding the row, and commits nothing unless it's still `locked` or `scored`, since a handler past its lease can run twice and a cancel can land after the first look. Then `runPriceUpdate`; the game event becomes **`final`**; `recomputeTotals` from the event; `recomputeStandings`; on a `next_open` skip the warning review item `prices_carried`, keyed `prices_carried:<gameId>:<eventId>`; and if the next game event is `upcoming`, `game_open` for it, due now, under `game_open:<gameId>:<eventId>:final` (the planned key is already taken).

Totals and standings follow the status change because both take `final` from the game event.

**If `game_finalize` never finishes.** The job is queued once, so a dead one would leave the event non-final for good, as would a game event that locked after its event completed, which never had a job, and one whose event was cancelled after the lock, which never gets one either (3.9). `planGameJobs`, which the daily `sync_calendar` job runs for every game of its season, sweeps all three, like the lock and open sweeps: a `locked` or `scored` game event whose event is `completed` or `cancelled` and that has no `game_finalize` job pending, running or waiting to retry gets `game_finalize:<gameId>:<eventId>:sweep:<yyyy-mm-dd>`, due now, at most once a day.

**`game_open`** waits for the previous game event to be `final`, or for the 24-hour cutoff, whichever comes first.

**After `final`,** a correction still re-scores through the same jobs. The game event stays `final`, its totals and standings stay `final`, and prices don't move (3.5).

**`game_checks`, the daily checks.** `sync_calendar`, after its planning and after queueing the next day's sync, queues `game_checks:<gameId>:<yyyy-mm-dd>`, due now, with the payload `{ gameId }`, for each of the season's `running` games. It's a job of its own, so a check that fails is retried alone and can't stop the calendar chain. The handler (`src/game/corrections.ts`) runs the three steps below in order, and any of them can run twice:
- **`checkScoreExplanations(db, now, { gameId, sample = 200 })`:** for a random sample of the game's teams with a lock record, each event's `team_base_lines` plus `team_adjustment_lines` must equal its `team_event_totals.points` (0 with no row, so a lost row shows). Only events that are `locked`, `scored` or `final`, and not one where a session's latest live run is `running` or `failed`: totals disagree mid-run by design, and the recovery repairs a failed run, and one statement reads the runs and the ledger, so they're of one moment. Each event found wrong, earliest first, in its own transaction, opens the blocking review item `score_mismatch` and rebuilds inline: `recomputeTotals` from that event, then `recomputeStandings`. Every wrong event is rebuilt, since a rebuild rewrites later events' running totals but not their points. The item's key, `score_mismatch:<gameId>:<eventId>`, is unique only while open, so a new mismatch opens a new item once the old one is resolved. It has no session, so it moves no session status, but it holds an unfinished event's finalization until an admin resolves it.
- **`recoverScoringRuns(db, now, { gameId })`:** a dead `teams` or `standings` step leaves new asset lines, mixed team lines and old totals. Before `final`, finalizing repairs that. After it, the dead job's key blocks a re-queue, and a worker that died on its last attempt leaves the run `running`, so the check above skips the event for good. For a `running` game, this:
  - fails (`failRun`) each live run still `running`, more than an hour old, with no `score_session` job alive for it. Alive is `pending`, `running` or `failed`, and "for it" is a later step of that run, or an `assets` job for its session, which would start again;
  - queues each session whose latest live run failed and has no job alive, under `score:<gameId>:<sessionId>:retry:<yyyy-mm-dd>`, so at most once a day, with `force`. A run that died before its asset lines never became current, so the current run can be a `succeeded` one with the same fingerprint, and an unforced retry would skip for ever. A `final` game event takes the re-score as it takes a correction: it stays `final`, and prices don't move. `enqueueScoring` queues nothing for a session under review or cancelled;
  - opens the warning `scoring_retried`, keyed `scoring_retried:<gameId>:<sessionId>`, unique while open, for each run it failed or session it queued.

  It runs after the check, so a stuck run, which the check skips, is repaired without a false `score_mismatch`. The check also skips an event whose latest run on a session failed, since the recovery repairs that and the next day's check verifies it. Dry runs are never touched. An inline run of `finalizeGameEvent` has no `score_session` job, so one still going after an hour is failed; its next step throws, and `game_finalize`'s retry starts a new run.
- **`pruneLineupVersions`:** see 3.7.

**Cost at 250k teams:** steps 2–4 are a few set-based queries over about 1.75M lineup rows and about 1.25M memberships. That's seconds to a minute of database time per run, and it doesn't grow with how many people are browsing.

### 4.9 Corrections to the rules or the code
- **A misconfigured rule** (a wrong points value discovered mid-season): ruleset versions are frozen once used (3.2), so nothing can be silently edited. An admin publishes a **correction version** and explicitly re-points the affected past events to it. That's audited, and it re-scores those events. *This adds one admin action to Part 3's freeze rule. It stops silent edits, not deliberate, visible corrections.*
- **A bug in the scoring code:** the fix bumps `engine_version`, which changes every fingerprint. An admin first runs a **dry run** across the season. The diff summary shows how many teams' points would change, and by how much. The live re-score runs only after the admin approves. Players then get a correction notice that names the reason.

**As built** (`src/game/corrections.ts`). All three are staff actions: each takes a reason that isn't blank and is audited in its transaction.

**`publishCorrectionVersion(db, now, actor, { gameId, params, rules, notes, eventIds, reason })`** returns `{ rulesetVersionId }`. One transaction, holding the game row and the listed game events:
- It refuses, writing nothing, no rules (the re-score would wipe the events' points), an empty list, a game that isn't `running` (`game_not_running`: nothing would re-score it), or any event that isn't `locked`, `scored` or `final` in the game.
- It adds a version with `is_correction` set, numbered after the game's latest and effective from the first listed event by sequence, with its rules.
- It re-points the listed game events. `game_rules_10` lets this past the freeze (3.2) only while the transaction has `gridlocked.ruleset_correction = 'on'`: `set_config(..., true)` makes that die with the transaction, and it's turned off again straight after the update, so it covers that one statement even inside a caller's transaction.
- It audits (`ruleset_version.correct`, with each event's previous version in `before`), then queues a re-score of every scored session of those events (4.8).

Only the listed events move. Later events stay on their version: `planGameEvents` leaves out correction versions, which would otherwise look like a version starting from an event that has locked (a `ruleset_version_refused` warning), and frozen rows are never replanned. Lock records keep the version they locked under (`team_event_states.ruleset_version_id`), and the game's invariant checks read an event's lock rules from there, and flag any lock record on a correction version. A correction also never sets `teamsPerUser` for new teams (3.6). Points change and prices don't (3.5): nothing here runs the price formula.

**`dryRunGame(db, now, actor, { gameId, reason })`** returns `{ runIds, sessions, assetsChanged, teamsChanged, biggest }`. One transaction starts a `dry_run` run (trigger `admin`) for every scored session and audits (`game.dry_run`). Then, an event at a time and outside that transaction, `dryRunEvent` scores each session with the current engine and the event's rules, keeping the lines in memory, and works out every team with a lock record, in batches, through the code a live run uses. It writes each run's `diff_summary` and no lines, adjustment lines or totals.
- **Assets** compare against the current lines (`asset_session_totals`), as a live run's do.
- **Teams** compare against the stored `team_event_totals.points`, session by session in order: the sessions before as re-scored and those after as they stand, which is what the live re-score writes at each step. So a run's `teamsChanged` and `biggest` are what its session changes, and a team's changes over an event add up to the event's whole change.
- **What it returns:** `assetsChanged` and `teamsChanged` are different assets and teams, and `biggest` is the 10 biggest changes of any session.
- A dry run never supersedes a live run, nor a live run a dry one. A newer dry run takes over from one still going, which throws; an error marks the run's `running` rows `failed`.

**`approveRescore(db, now, actor, { gameId, reason })`** returns `{ queued }`. It refuses (`dry_run_required`), writing nothing, unless a `dry_run` run of the game has `succeeded` at the current `ENGINE_VERSION`. It audits (`game.rescore_approved`) and queues a forced re-score of every scored session (4.8).

"Every scored session" is `scoredSessions`: what `enqueueScoring` accepts, in a `running` game.

### 4.10 Indexes beyond keys
- `asset_score_lines (game_id, session_id)`: the per-session replace and the team view join. Served by the leading columns of its unique key (4.2), so there's no separate index.
- `team_adjustment_lines (game_id, event_id)` and `(team_id, event_id)`: batch recompute and one team's explanation.
- `team_event_totals (game_id, event_id, global_rank)` and `(team_id, event_sequence)`.
- `league_memberships (team_id) WHERE left_at IS NULL`: "my leagues" and the 50-league cap.
- `league_memberships (league_id) WHERE left_at IS NULL`: standings. Served by the leading column of the partial unique key (4.6), so there's no separate index.
- `league_standings (league_id, rank)`.
- `scoring_runs (game_id, session_id) WHERE is_current`: the partial unique index of 4.1.

## Part 5. Community (proposed)

This part covers the forum, live session chat, votes, spoiler state, moderation and notifications. It follows HLD §7 and §10. Two decisions shape it, both made 2026-10-27:
- **Deleted accounts are always anonymized.** Posts stay, the author shows as "deleted user", and personal data is removed. Before leaving, a user can still delete individual posts.
- **Chat is archived after 30 days.** A session's chat moves to a compressed, read-only file in object storage. It can still be replayed under its thread, but it's no longer searchable.

### 5.1 How deleted users work (affects every table here)
- **A deleted account becomes a tombstone, not a missing row.** The `users` row stays, so every foreign key still holds (0.7: `ON DELETE RESTRICT`). Its personal data is scrubbed: email, name, avatar, profile fields, sign-in accounts and sessions. Its status becomes `deleted`.
- **Anywhere an author is shown, a deleted author renders as "deleted user".** There's nothing to rewrite in posts, chat or archives, because they store only user IDs and names are looked up when displayed.
- **Teams and leagues follow the same rule:**
  - A deleted user's teams are retired and renamed "Deleted team" (3.6).
  - A league they owned stays active, and admins can reassign the owner (4.5).
  - The mechanics are in Part 6.
- **For your lawyer (HLD §13.6):** after scrubbing, the tombstone is a random ID with no personal data. But a post's text can itself contain personal data. Requests to remove specific posts are handled through support with a moderator `remove` action.

**`broadcasts`:** messages for everyone.
- Columns: `game_id` or none, `kind`, `session_id`/`event_id`, `data`, `created_at`.
- Examples: "provisional scores are in", "Qualifying thread is live", site announcements.
- **These aren't copied into every user's inbox.** The bell merges a user's notifications with broadcasts newer than their `broadcasts_read_at` (Part 6). Telling 250k users that scores are in writes one row, not 250k.

**`notification_preferences`:** (`user_id`, `kind`, `channel`: `in_app` or `push`, `enabled`). Only overrides are stored; defaults live in config.

**`push_subscriptions`:** `id`, `user_id`, `endpoint` (unique), `p256dh`, `auth`, `user_agent`, `created_at`, `last_success_at`, `failure_count`. It's pruned on HTTP 410, and push fan-out is batched (2.10).

**`email_outbox`:** account emails waiting for the daily cap (HLD §10).
- Columns: `id`, `to_email`, `template` (`verify_email`, `magic_link`, `password_reset`, `email_change_notice`, `delete_confirm`), `payload` (jsonb, default `{}`), `status` (`queued`, `sent`, `failed`, `expired`), `attempts`, `send_after`, `provider_message_id`, `created_at`, and three nullable ones added in M5: `sent_at`, `expires_at` (a magic link or reset past it is `expired`, not sent) and `last_error`.
- **`to_email` is nullable** because a sent or expired row's address can be scrubbed (6.7), but a CHECK requires it while `status = 'queued'`.
- **One queued row per address and template:** a partial unique index on `(lower(to_email), template) WHERE status = 'queued'`, so a repeat request doesn't queue a second email. An index on `(status, send_after)` serves the sender.
- **Magic links and resets go first**, since they expire. Verification emails wait if the cap is near.
- **How the outbox works (M5):**
  - `queueEmail` first limits each address to 3 emails per template in 10 minutes, on a SHA-256 of the lower-cased address (`auth_rate_limits` key `email:<template>:<hash>`, so no address is stored there). Past that it writes nothing and returns `limited`, which no caller shows.
  - It then upserts the queued row (a repeat replaces it) and sends at once if the caps allow, under a Postgres advisory transaction lock so two requests can't both take the last place. Over the cap, with no sender, or on a passing failure, the row stays `queued` with a later `send_after` and an `email_flush` job is queued for that time (key `email_flush:<yyyy-mm-ddThh>`).
  - **Caps** (setting `email_caps`: `perDay` 100, `perMonth` 3,000, `reservedForUrgent` 20, `alertAt` 0.8). Days and months count in UTC from `sent_at`. Ordinary templates stop at `perDay - reservedForUrgent` (80); `magic_link`, `password_reset` and `delete_confirm` can use all 100; the month's cap binds even when the day has room. The flush sends urgent rows first, then oldest, and marks a row past `expires_at` `expired`.
  - **A queued row holds a live link.** A queued `magic_link` row's payload is a working sign-in link for at most 15 minutes (its `expires_at`), until it is sent or scrubbed. A verification or reset link lasts at most 1 hour.
  - **A finished row keeps no personal data:** when a row becomes `sent`, `failed` or `expired`, `to_email` is set to null and `payload` to `{}`. The template, status and timestamps stay. `last_error` holds a short code (`rejected`, `send_failed`, `provider_cap`), never provider text.
  - The Resend `Idempotency-Key` is the row id, so a crash between the send and the update can't send twice. A 422 is a rejected address (`failed`, not retried); a quota error from Resend holds the batch until the next UTC day; other errors leave the row queued for the next hour.
  - At 80% of `perDay` a review item `email_cap_near` opens, once per UTC day (key `email_cap_near:<yyyy-mm-dd>`).

### 6.0 What Better Auth provides (checked against its v1.6 docs, 2026-10-27; installed and re-checked at 1.7.18, 2026-11-07)
- **Renaming:** core tables and columns can be renamed with `modelName` and `fields`. That's how 0.1's names work: `users`, `auth_sessions`, `auth_accounts`, `auth_verifications`, and snake_case columns.
- **IDs:** generated by our own function (`advanced.database.generateId`), so auth rows get UUIDv7 like everything else (0.2).
- **Admin plugin:** adds `role`, `banned`, `ban_reason` and `ban_expires` to users, and `impersonated_by` to sessions. Custom roles are defined through its access-control config.
- **Rate limits** can be stored in the database (`rateLimit` model). That's needed on serverless hosting, where memory doesn't last between requests.
- **Built-in account deletion is a hard delete, with hooks.** That conflicts with "always anonymize" (5.1), so **we leave it disabled and use our own scrub flow** (6.7). `deleteUser.enabled: false` still leaves `/delete-user` routed (it answers 401), so both paths are also in `disabledPaths` and answer 404.
- **Installed at 1.7.18** (`better-auth` and `@better-auth/drizzle-adapter`, pinned exactly). Sign-up, sign-in, session reads and impersonation run through the adapter against the tables in 6.1 as they are, with no schema change: `auth_sessions.impersonated_by` as a uuid foreign key (ON DELETE SET NULL) takes the admin's id, and ids are UUIDv7 from `generateId`. The adapter is told our names with `modelName` (`users`, `authSessions`, `authAccounts`, `authVerifications`, `authRateLimits`); `authTwoFactors` joins when the two-factor plugin does.
- **Admin routes:** every `/admin/*` path is in `disabledPaths`, since staff writes are ours, in one transaction with their audit row (6.6). Impersonation still uses the plugin's `impersonate-user` and `stop-impersonating`, but only through `auth.api`, from `startImpersonation` and `stopImpersonating` (6.4). Over HTTP an admin could start one without the staff two-step, a reason or an audit row. (Changed by M5 Task 8; before, those two were open.)
- **Two-factor plugin:** `twoFactor({ issuer: "Gridlocked", allowPasswordless: true, totpOptions: { period: 30 } })` on `auth_two_factors` (`modelName: authTwoFactors`). `allowPasswordless` because a Discord or magic-link staff member has no password to confirm with. It challenges password sign-in only, which is why staff tools have their own step (6.4).
- **The IP for rate limits** comes from `x-vercel-forwarded-for`, then `x-forwarded-for`. With neither, Better Auth warns and shares one bucket per path.

### 6.3 Usernames
- **Format:** 3 to 20 characters from `A-Z a-z 0-9 _ .`. No spaces, accents or look-alike scripts (a Cyrillic `а` is refused).
- **Unique and case-insensitive:** a unique index on `lower(username)`. Better Auth's username plugin stores `username` in lower case and keeps `display_username` as typed, so "taken" holds whatever the case. The check says why a name is refused, in this order: `format`, `reserved`, `taken`, `held`.
- **Reserved names** come from two places, both read live:
  - `filter_rules` with `scope = usernames` and `active`: `admin`, `moderator`, `gridlocked`, `system`, `support`, and **official-looking patterns** such as `F1`, `Formula1`, `FIA` and `official`. That matters because a username like "F1_Official" would undercut the not-affiliated stance (HLD §13.4). A `word` rule matches the whole name; a `regex` rule matches anywhere, case-insensitively.
  - Every driver's and constructor's name in the reference tables (family name, full name, display name, slug, and a team's name), so a new driver is covered without a seed.
  - Look-alikes are compared, not stored: lower case, with `_ . - ` and spaces dropped, `0`/`o` alike and `1`/`i`/`l` alike (one skeleton, so any mix meets). `F1_0fficial` and `f1official` are alike. A rule is tried against the name as typed, with zeros read as `o`, and fully normalized.
  - Driver and team names are reserved as whole names (exactly, after normalizing), not as substrings: `Ferrari_Fan` is allowed, `Hamilton` is reserved for everyone. Word rules and these names are compared by skeleton.
  - The display name must equal the username ignoring case, at sign-up and in `changeUsername`, so a reserved name can't hide there.
  - A blocked name can be appealed through moderators.
- **Changes are limited:** once every `username_change_days` (a setting, default 30). **`username_history`** (`user_id`, `username`, `changed_at`) keeps old names. An old name stays held for 90 days after `changed_at`, so nobody can grab a just-abandoned name to impersonate its owner. The hold is against other people: a user can take their own old name back.
- **`changeUsername` is the only rename path:** one transaction that locks the user row, refuses with `username_too_soon` inside the wait, writes the history row and sets `profiles.username_changed_at`. Two people racing for one name both pass the check; the unique index lets one in and the other gets `taken`. Changing only the capitals of your own name updates `display_username` alone: no history row, no wait. Choosing a first name (none before) starts no wait either. Better Auth's `/update-user` refuses `username` and `displayUsername`, and `/sign-in/username` and `/is-username-available` are disabled.
- **Mentions survive renames.** `post_mentions` stores the user ID (5.4). The post text keeps the old `@name` as written, and the mention link still points at the right person.

### 6.4 Roles, staff security and impersonation
- **Roles** (`users.role`): `user`, `moderator`, `admin`, `system`. Permissions are defined in code and reviewed, not in a table: `ROLE_PERMISSIONS` in `src/identity/roles.ts`, in the admin plugin's statement names, which `auth.ts` turns into its access-control config (`createAccessControl`, roles `user`, `moderator` and `admin`). No role has `impersonate-admins`.
- **Role changes are admin-only and audited** (6.6). `setRole` is one transaction with the audit `user.role.update` and a reason. It refuses `system` as the new role or the target (`role_reserved`) and leaving no active admin (`last_admin`: an admin who isn't banned and isn't deleted). Every admin row is locked in id order before the target, so two admins demoting each other wait for one another rather than deadlock; a deadlock Postgres still breaks is retried, then reported as `try_again`. It revokes the target's sessions, and any they hold as someone else, so the new role holds from the next request. Until M8's screens it runs through `pnpm staff set-role` (by username, with no event; the output shows only the username and the role change). Trust level is separate from role (HLD §3.2).
- **Bans:** `banUser` sets `banned`, `ban_reason` and `ban_expires` (null: until lifted), revokes the sessions and writes the audit `user.ban`, in one transaction; `unbanUser` writes `user.unban`. The admin plugin refuses a banned user's next sign-in, however it's made, and lifts a ban whose end has passed. The last active admin can't be banned. M7 adds the `mod_actions` mirror (5.9).
- **Staff accounts must use two-factor sign-in (decided, M5 decision 5).** An admin or moderator without TOTP set up can sign in, but staff tools stay locked until they enable it (`staff_two_factor_required`). Staff accounts are the most damaging to lose.
- **The staff two-step, once per session (M5 finding 3, ruling 34).** The two-factor plugin only challenges password sign-in, so a magic link or Discord would skip it. Staff tools therefore ask for a code once per session, however the person signed in. `verifyStaffSession` checks a TOTP code at the caller's `now` (RFC 6238 with the plugin's settings) or uses up a backup code, then sets `auth_sessions.staff_verified_at`, audited as `staff.session.verify` (the method, never the code). It's the only thing that sets it: no sign-in does, password and TOTP included. Five failed attempts per user per 15 minutes, then every attempt waits for the window (`rate_limited`); a right code costs nothing. Each attempt is counted by one atomic upsert before its code is checked and given back if the code is right (ruling 40), so a burst of attempts at once can't all slip under the limit. Counted in `auth_rate_limits` under `staff-verify:<user id>`. `requireStaff(viewer, "moderator" | "admin")` refuses, in order: no viewer, an impersonated session (`read_only`), a banned or non-staff role, or a moderator at an admin check (`forbidden`), no TOTP, and an unverified session (`staff_session_unverified`). A new session starts locked; signing out and back in locks it again.
- **The factor itself is managed only from an unlocked session (ruling 37).** For a moderator or admin with TOTP on, `hooks.before` (looking the session up by token alone, with no expiry test of its own, so a clock running ahead of Better Auth's can't make it fail open) refuses every session-authenticated `/two-factor/*` path (enable, disable, backup codes, the TOTP URI, and any path a later release adds) with 403 `STAFF_SESSION_UNVERIFIED` until the session has `staff_verified_at`. Otherwise a session alone could mint backup codes or enrol another authenticator and unlock itself: with `allowPasswordless`, a Discord or magic-link staff member has no password to ask for. First enrolment stays open, since there is no factor yet, and the sign-in challenge has no session, only the two-factor cookie. The cost: a staff member unlocks before managing their own codes.
- **Impersonation** (admin plugin; for support, e.g. "see what this user sees"):
  - admins only, from a verified session (`requireStaff(viewer, "admin")`); never another admin, the system user or yourself (`cannot_impersonate`);
  - limited to one hour (`impersonationSessionDuration: 3600`), held on the server (ruling 38): the session update hook never moves `expires_at` past `created_at` + 1 h for a session with `impersonated_by`, and `getViewer` treats one older than an hour, by the request's `now`, as signed out. The plugin's own limit relied on a `dont_remember` cookie the client could drop;
  - never of a banned user (`cannot_impersonate`), and only from the session the request carries: `viewer` and the headers must name the same one;
  - every start and stop is audited (`user.impersonate.start` with a reason, `user.impersonate.stop`), with the admin as `actor_user_id` and the user as `impersonating_user_id`. Signing out of it counts as a stop and is audited the same way;
  - `stopImpersonating` puts the admin's own session back, still verified, even if the stop row can't be written (that failure is logged by name only);
  - a visible banner shows while it's active;
  - the impersonated session is read-only. `hooks.before` refuses every non-GET auth path for a session with `impersonated_by` except `/sign-out` and `/admin/stop-impersonating` (so email, password, 2FA and account changes, whatever endpoint a later release adds), and `requireWritable` refuses our own writes (`read_only`).

### 6.5 Trust levels (HLD §7.4)
- **A daily job** recomputes the level of each active profile seen in the last 30 days (`last_seen_at`), in batches of 1,000 ordered by user id. The level comes from days visited, posts, reputation, upheld flags and account age. It skips `trust_level_locked` users and deleted profiles.
- **The thresholds are the `trust_thresholds` setting.** A level needs all four numbers: days visited, posts, reputation and account age. The starting values (M5, a call to revisit once real forum use exists):

  | Level | Days visited | Posts | Reputation | Account age (days) |
  |---|---|---|---|---|
  | TL1 | 3 | 10 | 0 | 3 |
  | TL2 | 15 | 50 | 25 | 15 |
  | TL3 | 60 | 200 | 200 | 60 |

  A user gets the highest level whose numbers they all meet.
- **Posts and upheld actions come from the forum (M7).** Until then the job's counts return zeros, so everyone stays at TL0; the forum passes real counts without changing the job.
- **Automatic demotion** only happens after upheld moderation actions (the level is then recomputed from the counts, so it can fall). Going quiet never lowers a level.
- **A moderator's change** (`setTrustLevel`) sets the level, sets `trust_level_locked`, and writes the history row (source `moderator`, `changed_by`, a required reason) and an `audit_log` row (`user.trust_level.set`) in one transaction. Clearing the lock (`user.trust_level.unlock`) is audited too and leaves the level as it is.
- **`trust_level_changes`** (`user_id`, `from_level`, `to_level`, `source`: `auto` or `moderator`, `changed_by`, `reason`, `changed_at`) gives a readable history, and the user can see their own. The job writes a row only when the level moves, so a second run the same day writes nothing.
- **The daily identity job** (`identity_daily`, key `identity_daily:<yyyy-mm-dd>`) is queued by `sync_calendar` once a UTC day, however many games there are. It runs these steps in order, each in its own transaction: trust levels, the purge of incomplete accounts (5.1), and the prune. A step that fails is logged by name and error name only, the rest still run, and the job then fails so the runner retries. The prune deletes expired `auth_sessions`, `auth_verifications` and `auth_rate_limits`; finished `email_outbox` rows (`sent`, `failed`, `expired`) older than 35 days, so the month's cap count (5.11) is unaffected; and the `username_history` of deleted profiles older than 90 days, which releases a tombstone's old names (6.3). A live user's history is never pruned.

**The registry (built in M5).** `PERSONAL_DATA` in `src/identity/personal-data.ts` has one entry per user column: the table, the column, what deletion does (`delete`, `scrub`, `retire` or `keep`, with why) and the export section it feeds, if any. The export and the deletion both walk it, in its order. A test walks every table in the Drizzle schema (`getTableConfig`) and fails for any foreign key to `users` with no entry, so M7's tables can't be missed by either. Two entries aren't foreign keys but are keyed by the address: `auth_verifications` and `email_outbox`.

**Export:** `requestExport` allows one open request per user and one a day (`export_pending`, `export_too_soon`); a request still open after a day counts as failed. It queues the `privacy_export` job, which builds one JSON file from the registry, stores it at `exports/<request id>.json` in the `exports` bucket (neon.ts), signs a 7-day download link, sets the request `completed` with `export_expires_at` and `export_url`, and emails the link (`export_ready`, an email row expiring within a day). The file has:
- the account and profile, the sessions (times, IP and browser) and the sign-in methods (provider names, not tokens);
- teams, with their lineups, chip plays and league memberships, and the leagues the user owns;
- old usernames, legal acceptances, trust level changes (with the moderator's reason, not who made them; DM 6.5) and privacy requests.

It never holds a token, hash, secret, password or two-factor data: every reader names its columns. A job for a deleted account stops and writes nothing. The job records `export_object_key` (always `exports/<request id>.json`) in its own committed write before it writes the file, so a run that dies after the write still leaves a row pointing at it. The daily `expireExports` step (`identity_daily`) deletes the file, by that key, once its 7 days are up, at the next run for a deleted account, and for a request that is `failed` or still open a day after it was asked for; then it clears the key and the link, so each request is swept once.

Deleting an object doesn't erase it at once: Neon Object Storage soft-deletes it on the current branch, so it stays in the branch's history, as Postgres rows do in point-in-time history, for the branch's history window. Neither this document nor `neon.ts` sets that window, so it is the project's default.

**Moves to M7, through the same registry:** posts, including revisions, and chat, including archived chat (5.5); votes, watch marks, notifications, push subscriptions and notification preferences. Each table registers its user column, how deletion treats it and its export section.

It covers GDPR and CCPA access requests (HLD §13.6).

**Deletion (our flow, not Better Auth's built-in one):**
1. **Confirmation:** `requestDeletion` takes the username typed out (any case; `wrong_username` otherwise), or the email address for an account that never chose a username (any case), and is offered an export first. With a verified address it emails a one-hour link (`delete_confirm`); only the token's hash is kept, and a new request replaces the old link. `confirmDeletion` uses the token up in the same transaction as the scrub; an expired, used or replaced link changes nothing (`invalid_link`). With no verified address, a sign-in in the last 10 minutes (the session's `created_at`) is the confirmation, and the account goes at once (`sign_in_again` otherwise). An impersonated session can't ask.
2. **One transaction, the scrub (`scrubAccount`),** in registry order:
   - pending sign-in, reset and magic links for the address or the id are deleted; queued and retrying outbox rows to the address are deleted, and finished ones keep their place in the month's count under the tombstone address;
   - all `auth_sessions` (including any the user holds as someone else), `auth_accounts` and two-factor rows are deleted;
   - the email becomes `deleted-<id>@deleted.invalid`, which keeps the email unique; name, username, display username, image and any ban are cleared, and the role becomes `user`;
   - profile fields go back to empty or their defaults, and `status = deleted`.
3. **Game data:** the user's teams are retired and renamed "Deleted team", and every open league membership ends. Past lock records and standings keep them. Leagues they owned stay active with no owner until an admin reassigns them (4.5).
4. **Personal leftovers removed:** pending email outbox rows, privacy request links and token hashes (the export file goes at the next daily run). M7 adds notifications, push subscriptions, notification preferences and watch marks.
5. **What stays, tied to the tombstone ID:** legal acceptances, trust level changes (reason included), and staff columns (filter rules, settings, exceptions, overrides, reviews, the audit log). In M7: posts and chat (anonymized), votes (counted but never shown per user), and reports they filed. Moderation history about them stays for the 2-year retention period (5.10).
6. Audit entry: `user.delete`, with the actor (the user, or a moderator with a reason, e.g. an under-16 account; a staff deletion must give one) and no address or name. M8 adds the rank rule: a moderator can't delete staff.

It refuses the `system` user (`role_reserved`) and the last active admin (`last_admin`, the same check as `setRole`, with admin rows locked in id order). Deleting an account twice changes nothing. A tombstone can't sign in by any method: it has no sign-in rows, and `.invalid` addresses are refused for magic links and resets. Discord or the old address makes a brand-new account. The daily purge of unfinished sign-ups leaves tombstones alone.

The username is held in `username_history` for 90 days and then released (the daily prune).

### 6.8 `legal_documents` and `legal_acceptances`
- **`legal_documents`:** `id`, `kind` (`terms`, `privacy`, `community_rules`), `version`, `published_at`, `requires_reacceptance` (boolean), `url`. The documents themselves are pages on the site, written with your lawyer (HLD §13).
- **`legal_acceptances`:** `user_id`, `document_id`, `accepted_at`. Recorded at sign-up. When a new version `requires_reacceptance`, users are asked again on their next visit.
- **Seeded:** the migration inserts `draft-1` of `terms`, `privacy` and `community_rules`, at `/legal/<kind>`, until the lawyer's text replaces them.
- **What is pending:** per kind, the latest document, unless the user has accepted a version at or after the newest one that `requires_reacceptance` (or the first, when none does). A new version without the flag asks nobody who already agreed to an earlier one; a user who never accepted is asked for the latest.
- **The gate:** `Viewer.complete` needs a username, `age_confirmed_at` and nothing pending. The email form's `/sign-up/email` refuses a body without `ageConfirmed` and `accepted` both true, and `completeSignUp` (one transaction: the age, every current document, and a first username if there is none) runs after Better Auth's sign-up commits. If that is lost, the account is simply incomplete. Discord and magic-link users start incomplete and finish on "Finish signing up". `acceptDocuments` records a re-acceptance.

### 6.9 Ready for ads later (HLD §16; nothing turned on at launch)
- **`consent_records`:**
  - Columns: `id`, `user_id` (nullable), `anonymous_id` (nullable, from the browser), `policy_version`, `choices` (jsonb: ads, analytics, …), `region`, `created_at`.
  - It records consent choices once a consent platform is added (HLD §16.3).
  - It's append-only, and the latest row is the current choice.
- **`feature_flags`:** `key`, `enabled`, `audience` (`everyone`, `staff`, `percent:N`), `updated_by`, `updated_at`. Ads sit behind a flag (HLD §16.4). So do features rolling out gradually, such as live chat if the spike says to stage it.

### 6.10 Indexes beyond keys
- `users (lower(username))` unique, and `users (email)` unique (Better Auth's).
- `auth_sessions (user_id)` and `auth_sessions (expires_at)`: revoke-all and pruning.
- `profiles (favorite_constructor_id)`, `(favorite_driver_id)` and `(country_code)`: auto-league membership upkeep (4.6).
- `profiles (status, last_seen_at)`: the nightly trust job considers only recently active users.
- `audit_log (entity_type, entity_id, created_at)`: "history of this event or override", and `audit_log (actor_user_id, created_at)`: "what did this admin do".
- `username_history (lower(username), changed_at)`: the 90-day reservation check.
- `privacy_requests (status) WHERE status IN ('pending','processing')`.

## Whole-model summary (all parts)

### Storage at beta size (about 500 users and 1,000 teams), for one season, including indexes
| Area | Estimate |
|---|---|
| Reference data and results (Parts 1–2), including snapshots | ~10 MB |
| Fantasy core (Part 3) | ~5 MB |
| Scoring and standings (Part 4) | ~20–40 MB |
| Community (Part 5), with chat in the database for 30 days only | ~30–60 MB |
| Identity and audit (Part 6) | ~2 MB |
| **Total** | **~70–120 MB**, about a tenth of the free tier's 1 GB. Archived chat lives in object storage, about 10 MB of 5 GB |

At the established and big sizes, the largest tables are post votes, lineup picks, team adjustment lines and posts. Each is already keyed for partitioning, and each is called out in its part's scale table.

### The decisions that hold the model together
1. **Facts, game and community never mix**, and foreign keys only point down (0.5).
2. **Anything that can change is versioned or append-only:**
   - rulesets;
   - lineups;
   - prices per event;
   - snapshots;
   - the audit log.

   History is never edited.
3. **Everything derived can be rebuilt from source:** totals, standings, ranks, caches and auto-league memberships.
4. **The database enforces the rules that matter:**
   - the lock deadline, through `app_now()`;
   - squad composition and budget;
   - one chip per race and once per season;
   - teams per user;
   - seat overlaps and car numbers.
5. **Shared work is done once:** asset scores are shared by every team, broadcasts by every user, and price lists by every builder. That's what lets the big size work without a redesign.
6. **Things that can't be undone are tombstoned, never deleted:**
   - users;
   - cancelled events;
   - retired teams;
   - removed posts.

### Deliberate limits (0.8)
- One series (F1).
- One scoring ruleset per game, so no per-league scoring (your decision).
- No late entry within a weekend (your decision).
- No head-to-head leagues (decided non-goal).
- No direct messages (5.16).

Each has its cost-to-change written down.
